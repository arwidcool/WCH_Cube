## Why this part needed a new mechanism

`data/FORMAT.md` opens with the idea the whole schema rested on:

> **Alternate functions are never listed per pin.** They live only in each peripheral's
> `remaps:` table.

That holds for CH32V003/V005/V006 (one AFIO_PCFR1 field per peripheral) and CH32X035 (one
`GPIO_PinRemapConfig` macro per peripheral). On both, one register write moves every signal
of a peripheral together, so a `remaps[]` index is a complete, atomic, register-valued choice.

**CH32H417 is an STM32F4-style part.** Three independent sources say so:

1. **RM 9.3.2.2** — `GPIOx_AFRL`/`AFRH`, `AFRy[3:0]`: *"(y=0-7), Port X pin Y alternate
   function selection: 0000: AF0 … 1111: AF15."* Four bits **per pin**.
2. **The EVT header** exposes exactly that and nothing else:
   `void GPIO_PinAFConfig(GPIO_TypeDef *GPIOx, uint8_t GPIO_PinSource, uint8_t GPIO_AF);`
   with `GPIO_AF0`…`GPIO_AF15` (`data/sources/H417/Evt/EXAM/SRC/Peripheral/inc/ch32h417_gpio.h`).
3. **The datasheet's pin table is written per pin**, e.g. PB8:
   `TIM10_CH3(AF1)/TIM4_CH3(AF2)/I2C1_SCL(AF4)/PIOC_IO0(AF5)/I2C4_SCL(AF6)/USART6_RX(AF8)/…`

`AFIO_PCFR1` survives on this part but is no longer pin muxing: it holds `PD0_1_REMAP`,
`UHSIF_CLK_RM[1:0]`, the PIOC port map and four ADC external-trigger **source** bits
(TIM8 vs EXTI, not a pin).

### The cost, measured rather than asserted

`python tools/extract_h417_pins.py --audit`:

```
  signals with an AF code   : 418
  pin-AF assignments        : 950
  signals reaching >1 pin   : 294 of 418 (70%)
  ALL        418 signals -> 851,948,976,569,927,895,391 remaps: entries
```

USART1 alone reaches 2 × 4 × 4 × 2 × 2 = **128** legal combinations, none of which is a
register value. The two obvious shortcuts are both wrong, and both are round 5's own defect
class in the mirror — not *offered-but-impossible* but **possible-but-refused**:

- one remap per peripheral taking each signal's first pin would refuse ~70 % of the legal
  pin choices, on a 128-pin part whose whole purpose is "which peripheral reaches which pin";
- N remaps taking the i-th option would offer 7 of USART1's 128 as if they were the only ones.

The fixture is the proof: `CH32H417_QFN128_full.wchproj` puts `USART1_TX` on PD13 (AF14)
while `USART1_RX` stays on PB15 (AF4), and `SPI1_SCK` on PA5 (AF5) while MOSI/MISO stay on
PF8/PF9 (AF3). **A remap-shaped model cannot produce that configuration at all.**

## The extraction, and the four ways the conversion mangles a pin row

`packages:`, `pins:` and every `signal_pins:` block are **emitted** by
`tools/extract_h417_pins.py --yaml`, not transcribed. 284 package assignments and 950
pin-AF pairs cannot be hand-copied without an error, and an error here is invisible: a
wrong AF code compiles and the pin carries the wrong function on the board.

The PDF-to-markdown conversion mangles pin rows in **four** distinct ways, all silent:

| | shape | example |
|---|---|---|
| (a) | the pin NAME wrapped to its own line | `## - - 8` then `## PC13` |
| (b) | a leading `-` dropped, leaving two columns | `## 83 121 PB9` |
| (c) | the FIRST column wrapped to its own line | `## 68` then `## 83 121 PB9` |
| (d) | a SUBSCRIPT split — `VSS` became `V` then `SS` | `## 0 0 0 V` then `## SS` |

(b) and (c) look identical to a parser and mean opposite things. Reading the `## 83 121 PB9`
row as (b) drops PB9 from QFN68, giving **49** I/O where the datasheet says 50 — and that
one-pin error in a table of 284 was caught only by asserting the pin numbers run 1..68
rather than 1..max. (d) produced a package table containing a pin called `V`.

**The I/O counts are the independent check**: 50 / 65 / 95 from the extracted tables match
the DS model table's "GPIO port number" row for WEU6 / MEU6 / QEU6 exactly. That is the
same cross-check `validate_mcu.py`'s `io_count` rule performs, and it passing on all three
columns is what makes the extraction believable.

No shorted pin groups on any package, unlike CH32V003's SOP8 and CH32V006's QFN12/QSOP24.

## Source and code problems found while doing this

### 1. The datasheet contradicts itself about which family MEU6 and WEU6 belong to

Four statements, and the first is outnumbered three to one:

| Says | MEU6 (QFN88) | WEU6 (QFN68) | REU6 (QFN60X6) |
|---|---|---|---|
| DS p.1 model table | CH32H416 | CH32H416 | CH32H415 |
| DS Table 2-1-1 header | **H417MEU6** | **H417WEU6** | — |
| DS ch.4 ordering table | **CH32H417MEU6** | **CH32H417WEU6** | CH32H415REU6 |
| PlatformIO board ids | **genericCH32H417MEU6** | **genericCH32H417WEU6** | **genericCH32H417REU6** |

This file treats **CH32H417 as one part with three packages** (QFN68/88/128), because that
is what its own pin table is titled and what the ordering table and the toolchain both
agree with. Both affected variants carry a `notes:` saying so. AGENT-1 owns the final call.

Note the same model table is demonstrably **right** about I/O counts — it is what caught
the parser bug above. Use it for resources, not for identity.

### 2. Three documented pin types had no CSS rule, and nothing had ever used them

`data/FORMAT.md` lists `sys`, `nc` and `analog` as legal `pins[].type` values. The template
styled only `io`, `power`, `ground`, `reset` and `boot`. No shipped part had ever used the
other three, so a `sys` pin got no `rect` fill, kept the SVG default, and its label sat on
it at **1.14:1** — `legibility.test.js` caught 44 of them the moment this part's crystal
pads, Ethernet MDI pairs and USB SuperSpeed pairs arrived. Fixed in `app/template.html` by
giving `sys`/`analog` the same `--pin-sys` fill that `reset` and `boot` already use (a
pairing the suite has always checked) and `nc` the unused-pin fill.

### 3. `tests/codegen_compile.test.js` counted manual GPIO pins with `P[A-D]`

This part has ports **A–F**. A fixture made of PE/PF pins would have read as "0 manual GPIO
pins" and been rejected for exercising nothing. Same defect class as
`tools/extract_pins.py`'s old `P[A-D][0-7]`, which silently missed two thirds of CH32X035.
Widened to `P[A-Z]`, and the fixture now puts a pin on PE0 on purpose.

### 4. The firmware HAL and the generated `main.c` both named SDK functions this part renames

Three separate cases, all of which failed at **link** rather than at compile:

| | Everywhere else | CH32H417 |
|---|---|---|
| refresh `SystemCoreClock` | `SystemCoreClockUpdate` | **`SystemAndCoreClockUpdate`** (two cores) |
| printf with no pin | `SDI_Printf_Enable` | **does not exist** — `debug.h` has only `USART_Printf_Init(baud)`, which claims a USART |
| `RCC_ClocksTypeDef` | has `PCLK1_Frequency`/`PCLK2_Frequency` | **has neither**; it has `Core_Frequency` instead |

The HAL cases are now branches in `lib/wch_hal/`, and `lib/board/src/board.c` and
`src/main.c` go through the HAL instead of calling the SDK by name. The **generated**
`main.c` is the one that mattered for the product: it now reads `codegen.clock_update_fn`
and `codegen.sdi_printf_fn` from the MCU file, so no part is named in `app/engine/`. An
empty `sdi_printf_fn` means "this part has no SDI channel", and the generator emits a
comment saying so rather than a call that would not link.

`lib/wch_hal/src/wch_hal_gpio.c`'s `port_clock()` also fell off the end of a non-void
function for an unknown series — a warning and undefined behaviour. It is now an `#error`
naming what is missing.

### 5. `data/sources/H417/` did not match the documented layout

The DS and RM sat at the top level with an empty `datasheets/` beside them, and `evt/` was
lower-case, so `codegen.sdk: { evt: H417 }` would have resolved on NTFS and **failed on
Linux and in CI** — the `ch32v00X.h`/`ch32v00x.h` defect one directory up. Renamed to
`Datasheets/` and `Evt/` and every citation updated; `tests/source_paths.test.js` is green.

### 6. `PD0PD1_RM` describes pins this part bonds separately

RM 9.3.2.1 bit 0: *"Pin PD0&PD1 remapping bit … 0: Pins function as crystal oscillator
pins."* But DS Table 2-1-1 bonds PD0, PD1, XI and XO as **four separate pins** on all three
packages and gives PD0/PD1 full AF lists. This reads like text carried over from a smaller
part. Unresolved — it decides whether a future `clock.hse_signals` points at XI/XO or PD0/PD1.

## What is in the file, and what is not

**Twelve peripherals are modelled**: USART1–3, SPI1–2, I2C1–2, I3C, TIM1–4, plus SYS. That
spans five ports and AF codes 1, 3, 4, 5, 7, 9 and 14, which is what the mechanism needed
to be proven on real silicon rather than only on the synthetic part in
`app/tests/afmux.test.js`.

**This part has roughly 47 peripheral families and a 68,330-line reference manual.**
Everything below is absent on purpose rather than half-modelled, and each line says why:

| What | Why |
|---|---|
| ADC, HSADC, DAC, OPA, CMP, DFSDM | analog, and all of them need the clock tree first — an ADC prescaler with no PLL behind it would display a frequency that is wrong |
| ETH, USBFS, USBHS, USBSS, USBPD, SerDes | each is a chapter, and most claim dedicated pads rather than muxed GPIO |
| LTDC, DVP, GPHA, FMC/SDRAM, QSPI, SDIO, SDMMC, UHSIF, SAI, PIOC, SWPMI | the four largest are 73, 60, 28 and 15 signals; they are the ones that make a `remaps:` model impossible and are also the ones that want their own extraction pass |
| CAN1–3, I2C3–4, SPI3–4, USART4–8, TIM5/8–12, LPTIM1–2, RTC, IWDG, WWDG, RNG, ECDC, TKey | ordinary, and mechanical to add now that the mechanism exists |
| `exti:`, `dma:`, `nvic:` | absent entirely. This part has 16 EXTI lines, two 16-channel DMA controllers and a vector table nobody has read yet |
| the clock tree (`pll:`, bus prescalers, per-domain clocks) | RM ch.8 gives this part several PLLs and a far deeper tree than any CH32V00x. A partial `pll:` block would let the app compute and display a frequency that is wrong, which is worse than showing nothing |
| `analog:` and `five_volt_tolerant:` per pin | the DS's "I/O characteristic" column carries FT, A and SDP markers, and it is split across lines by the PDF. Extracting it wants its own pass; guessing it would put 5 V tolerance on pins that do not have it |
| `constraints:` | audited, none found in the twelve modelled peripherals: no per-pin note on any `GPIOMode_TypeDef` member, no shorted groups on any package, and nothing coupling a peripheral's state to a pin's legality |
| I3C's other five structs | `I3C_CtrlConfTypeDef`, `I3C_TgtConfTypeDef`, `I3C_DeviceConfTypeDef`, `I3C_CCCInfoTypeDef`, `I3C_FifoConfTypeDef` are protocol-stack state, not pinout configuration |

## Open — in the order they block each other

1. **Settle the family question** (problem 1). It decides whether this is one part or
   three, and therefore how many files exist. Everything else is cosmetic beside it.
2. **Re-derive the AF map from a second source** and diff to zero, the way
   `tools/extract_remaps.py` did for CH32V006 (232 assignments, 0 differences). DS Table
   2-2-x is per-peripheral where Table 2-1-1 is per-pin, so the two are genuinely
   independent readings of the same silicon. A hand-checked table is not evidence.
3. **The clock tree.** It gates every analog peripheral and it is the largest single piece
   of remaining work. Until it lands, `codegen.rcc` writes only `SW` and `HPRE` — note
   HPRE's run is **not** the CH32V00x one: codes `0xxx` all mean /1, then 1000..1111 are
   /2, /4, /8, /16, **/64**, /128, /256, /512. There is no /32; the sequence jumps 16 to 64,
   and reading it as a doubling run would put /32 on code 1100 and halve the bus silently.
4. **How the dual core is modelled.** QingKe RISC-V5F at 400 MHz plus RISC-V3F at 160 MHz,
   and `mcu.core` is one string (it currently names both). PlatformIO ships three board
   files per package — plain, `_V3F`, `_V5F` — and the framework a linker script per core.
   `data/firmware/platformio.ini` uses the plain id and says why.
5. **CH32H416 and CH32H415.** Table 2-1-2 and Table 2-1-3 are their own pin tables, on
   QFN60X6, whose geometry is already in `packages.yaml`. They are separate parts under the
   repo's own rule, and the extractor covers only Table 2-1-1 today.
6. **`pio run -t upload` has never happened.** The firmware and a generated project both
   build for `CH32H417QEU6`; nobody has put the binary on silicon. The DONE line reads
   **"builds, not flashed"**, in exactly those words.

## Round 5/6: the peripheral set, the vectors and the clock (AGENT-3, 2026-09-12)

The human's read was that this part looked half-built: most peripherals absent and the clock
stubbed. Both were true, and the reason for the second was deliberate rather than lazy - a
partial `pll:` would have let the app compute and display a frequency that is wrong.

**What this produced.** 13 peripherals became **78**; the file gained a 125-vector `nvic:`
block, all 73 `RCC_HB*Periph_*` clock-enable bits across this part's three buses, and a clock
tree that models everything the schema can hold. Two new tools, both audited:

| Tool | What it reads | Audit |
|---|---|---|
| `tools/extract_h417_setup.py` | vectors from `ch32h417.h` + the startup `.S`; DMA/EXTI from the RM | `--audit` cross-checks both cores and exits 2 on a mismatch |
| `tools/gen_h417_peripherals.py` | pins from AGENT-4's `extract_h417_pins.py`; settings per peripheral TYPE from the RM | `--missing` prints the gap; `--splice` writes it |

**The finding that matters most.** The two startup tables **do not align**:
`startup_ch32h417_v3f.S` starts at `.word _start` and `startup_ch32h417_v5f.S` does not, so
v5f's table is one entry short at the front. Reading v5f index-for-index against `IRQn_Type`
names the **wrong handler for every peripheral vector** - an interrupt that never fires, or
fires the wrong function, with nothing anywhere to say so. The extractor anchors on the
RISC-V ISA's fixed exception numbers (NMI = 2, HardFault = 3), pads the front when a file
omits leading slots, and prints the offset on every audit. `nvic:` takes handlers from v3f.

**Two smaller ones.** `validate_mcu.py`'s `_signals_routed_by()` read only `remaps:`, so on an
AF-muxed part `clock.hse_signals` failed whatever the file said - fixed to read both schemas.
And the DS gives `QSPI2_SIO0` on PF8 through **both AF4 and AF8**; `signal_pins:` keys by pin,
so one is used and the alternative is recorded in a `notes:` rather than dropped.

**Still open, and deliberately not guessed.** `params:` for the ~70 peripherals that have
none (each needs its `struct:`/`sdk_field:` and option macros traced to `ch32h417_*.h`), and
the four secondary PLLs plus the eight peripheral clock muxes, which need a schema that can
hold more than one PLL and a source CHOSEN per tap. Both are on `TASKS.md`; the clock gap is
also stated in the `clock:` block's own `notes:` so a reader of the data sees it.

## The AF map: cross-checked against the DS's own second reading

`data/mcus/CH32H417.yaml` carries ~950 pin/AF assignments, and until 2026-09-12 every one of
them came from ONE reading of the datasheet: **Table 2-1-1**, which is PIN-first. This
repository's rule is that a mechanical extraction is re-derived from an independent second
source and diffed - CH32V006's 232 remap assignments were confirmed that way with 0
differences - and this map had never been.

The DS supplies the second reading itself, and it is structurally independent. **Tables
2-2-1 .. 2-2-31** are PERIPHERAL-first: one table per peripheral family, giving each signal's
optional pins and AF code. Reading a pin's row top-down and reading a signal's row
left-to-right are different parsing problems over differently laid out text, so a bug in one
does not reproduce in the other. `tools/audit_h417_af.py` compares them as SETS (the two
tables list a signal's pins in different orders, which is not a disagreement) and reports
both directions separately.

**It found 14 real defects, and they were of three kinds.**

### 1. Signal names split across a line break (12 assignments, FIXED)

The PDF conversion wraps a long pin row, and the break sometimes lands INSIDE a signal name:

    ## LPTIM1_ETR(AF1)/LPTIM2_CH2(AF3)/I2
    ## C4_SMBA(AF4)/TIM5_ETR(AF6)/

Rows are accumulated line by line, so this became `... /I2 C4_SMBA(AF4)/ ...` and the parser
matched `C4_SMBA(AF4)` - a name that does not exist - losing the real `I2C4_SMBA(AF4)`.
Twelve assignments were lost this way: `I2C4_SMBA` on PD11, `DVP_D0` on PC6, `DVP_D4` on
PC11, `DVP_D5` on PD13, `DVP_VSYNC` on PB14, `LTDC_G5` on PC1, `SDO_D0` on PB14, and
`SDRAM_D20/D21/D22/D4/D7` on PF8/PF9/PF10/PE7/PE10.

Fixed in `tools/extract_h417_pins.py` (`repair_split_names`): the fragments are rejoined
against a dictionary of signal names taken from the 2-2-x tables, so the repair cannot invent
a name. **Worth recording that this bug had a second effect**: the fragments produced phantom
peripheral headings (`VP`, `C4`, `DC`, `DIO`), and `gen_h417_peripherals.py`'s MERGE map had
entries for them - so **DVP pins were being filed under the USB controller**. Removing those
keys and adding `check_merge_keys()` (which fails the generator if a key names no real DS
heading) is what stops it recurring.

### 2. A merge that replaced instead of uniting (many assignments, FIXED)

`gen_h417_peripherals.py` merged DS headings with `merged[target][name] = opts`, so when two
headings re-prefixed onto the same signal name, one silently overwrote the other. Two
instances, both real:

* `CAN: CAN1` - the DS spells the CAN pins `CAN_RX`/`CAN_TX` (no instance number) on the
  rows where the controller is the first one, and Table 2-2-13 attributes both to CAN1.
  Mapping that heading wiped CAN1's own RX/TX pins, leaving `CAN1_RX: PA13(AF5)` alone
  where Table 2-2-13 lists four.
* `SDRAM -> FMC` and `FSMC -> FMC` - both produce `FMC_A0`, `FMC_D0` and the other shared
  names, so whichever was processed second replaced the first.

Fixed by unioning with a pin/AF dedupe. `CAN1_RX` now carries PA11, PA13, PB6, PB8 and PD0.

### 3. Places where the DS's OWN two tables disagree (RECORDED, not resolved)

These are listed so that a reader knows the two readings differ, **not** so that somebody can
pick one later. Round 4's rule applies: where two sources disagree they answer different
questions, so both are recorded and neither is averaged.

| Signal | Pin | Table 2-1-1 | Table 2-2-x | Note |
|---|---|---|---|---|
| `LTDC_CLK` | PE14 | `AF13` | `AF14` | same pin, same signal, different code |
| `SAI_SD_A` | PC1 | `AF7` | `AF6` | same shape |
| `LTDC_B4` | PA15 | `AF10` | not listed | 2-2-28 omits PA15 for B4 |
| `SDIO_D0` / `SDIO_D1` | PB14 / PB15 | `D1` on PB15 | `D0` on PB14 | the two functions are SWAPPED between the readings |
| `USART8_CTS` | PF10 / PE10 | `PF10` | `PE10` | same signal, different pin |
| `USART8_RTS` | PF9 / PE9 | `PF9` | `PE9` | same shape |
| `QSPI2_SIOX0..3` | PB11-PB14 | `SIOX0`, `SIOX1` | `SIOX2`, `SIOX3` | same pins and AF codes, different SIOX NUMBERS |
| `QSPI1_SIOX3` | PF5 | `AF9` | (unparseable) | 2-2-25's cell reads `PF5AF9)` - a missing paren in the conversion |
| `I2S2_MCK` | PC6 | `SPI2_MCK AF5` | `I2S2_MCK AF5` | the SAME block under two names (SPI2 in I2S mode), so not a real disagreement |

**The file follows Table 2-1-1 in every one of these**, because it is the pin-first table and
this project models pins. `tools/audit_h417_af.py` exits non-zero when the difference set
changes, so a future DS revision or a parser change surfaces here rather than passing quietly.

# Round 5: three more defect classes, found by cross-checking the WHOLE file

The AF cross-check above compares pin/AF *pairs*, so it only sees what the DS writes as
`SIGNAL(AFn)`. Three further classes lived outside that reach. All three are fixed; the
first two now have gates (`tests/h417_dedicated.test.js`) rather than a one-off audit.

## 4. The AFIO_PCFR1 remap value read as part of the signal name (74 names, FIXED)

DS Table 2-1-1 is pin-first and WCH writes the remap field value into the name there. The DS
says so itself, in Note 3 under the table:

> The value after the remap function underline indicates the configuration value of the
> corresponding bit in the AFIO_PCFR1 register. For example, `UHSIF_CLK_1` indicates that the
> corresponding bit of the register is configured as 01b.

Read as a name, `UHSIF_CLK_1` is a second signal on a second pad. It is not: it is
`UHSIF_CLK` with the remap bits at 01. The pin-first read produced **74 signal names where the
datasheet has 62**, and two of the consequences were worse than duplication:

* `SDMMC_CMD_2` and `SDMMC_CMD_3` named the **same pad, PC10**, as two different signals - so
  the engine would report no conflict between two names for one wire. Four of SDMMC's eight
  data lines were split the same way.
* The same happened to UHSIF's 48 ports, where the DS's Table 2-2-16 gives one row per port and
  one column per remap.

Table 2-2-12 and 2-2-16 are the same datasheet read **signal-first** - one row per signal, one
column per remap, no suffix - so `gen_h417_dedicated_pins.py` now reads those for SDMMC and
UHSIF. Nothing is lost: those functions carry no AF code in either table (they are the pad's
own function), which is why they were in the dedicated-pins file to begin with.

## 5. A wrapped line lost a digit and left a trailing underscore (48 names, FIXED)

The PDF text extractor wraps a long name, so `UHSIF_PORT32_2` arrives as `UHSIF_PORT32_` with
the `2` on the following line. The digit was dropped and the name kept a trailing underscore -
`PORT33_`, `SDCK_` and 46 more, none of which appears anywhere in the datasheet. This is the
same class as the 12 line-wrapped names the AF audit found, but with no AF code to anchor a
repair on, so the AF audit could not see it. Reading Table 2-2-x avoids the wrap entirely.

## 6. `UHSIF_CLK` claimed the SWDIO pad (1 pin, FIXED)

The pin-first read gave `UHSIF_CLK` five pads; Table 2-2-16 gives it four and `PB9` is not
among them. `PB9` is the `USB2DM`/`SWDIO` pad, so the file was offering the debug pin as a UHSIF
clock route. Found by the same signal-first comparison - it is the one difference in that audit
that was a wrong *pin* rather than a wrong *name*.

## 7. 24 peripherals had no settings at all (REGRESSION, FIXED)

When the block grew from 13 peripherals to 78, the new ones were emitted with `settings: {}`.
`tests/completeness.test.js` requires every peripheral of every real part to offer at least one
setting with a choice - and it is right to: a peripheral with no mode row is one the user
cannot switch on, and one whose clock the generated C never enables. The emptiness was silent;
the gate is what made it visible, and `emit_peripheral()` now REFUSES to write a peripheral
with no settings rather than emitting an empty block.

The wording follows existing precedent rather than inventing per peripheral: `Mode` with
`[Disable, Enabled]` is what H417's own `HSADC` and `SERDES` already say and what CH32X035 says
for `PIOC` and `AWU`; `[Disable, Activated]` is CH32X035's for `DMA1`, `IWDG` and `WWDG`;
`EXTI`, `PWR` and `FLASH` are copied from CH32V006 and CH32X035; `FMC`'s NOR/PSRAM, NAND and
SDRAM rows are RM ch.40's own feature list; `SDMMC`'s bus width is RM ch.33's ("single-wire,
four-wire, and eight-wire configurations") and mirrors the hand-written `SDIO` above it.

## 8. Two peripherals never got their clock enabled (FIXED)

`codegen.periph_clock` keys a bit by peripheral name AND builds the macro as `prefix + key`, so
the key has to be both. On this part they disagree twice: the peripheral `USBFS` has the bit
`RCC_HBPeriph_OTG_FS`, and `OPA`/`CMP` share `RCC_HB2Periph_OPCM`. Keying on the SPL spelling
kept the macros valid but made `clockBitOf('USBFS')` find nothing, so **every generated project
that enabled USBFS, OPA or CMP was compiled without its clock enable** and the only trace was a
comment. The keys are now peripheral names with the SPL spelling in the domain's `sdk:`, and
`verify_sdk_names.py` reads `sdk:` too - so it fails on a wrong entry instead of demanding a
macro that does not exist.

# Round 5, continued: signals with a pin that no setting could reach

The user's report was that the ADC was "missing LOTS of pins and channels, so is the ADC2,
COMP and OPA". Every one was the same defect, and it was not confined to those four: **167
of CH32H417's routed signals could not be claimed by any setting choice.** `requiredSignals()`
derives every pin claim from the settings, so a `signal_pins:` row no setting names is
decoration - the pin grid cannot offer it, the conflict engine never sees it, and the
generated C never muxes it. Two ADCs, the comparator, the op-amps, the whole external memory
bus, all 49 UHSIF ports and the SerDes pair were in the UI as empty shells.

## 9. `FMC` claimed nothing (87 signals)

Its three rows were `NOR/PSRAM`, `NAND`, `SDRAM`, each `Disable`/`Enabled` with no `signals:`
at all, so the entire external-memory bus was unassignable. Now five rows, grouped by the
DATASHEET's own split - Table 2-2-14 `FSMC Pin Functions` and Table 2-2-15 `SDRAM Pin
Functions` decide where each signal goes:

* `A0..A12`, `D0..D31` and `CLK` appear in BOTH tables, so they are the shared bus and get
  their own rows. Splitting them per controller would make the engine report a conflict
  between NOR and SDRAM on `A0` - they are one bus, which is exactly why the DS lists it twice.
* only in 2-2-14: `A13..A25`, `NBL0..NBL3`, `NE1..NE4`, `NOE`, `NWE`, `NWAIT`, `NADV`, `NCE2`, `INT2`
* only in 2-2-15: `BA0/BA1`, `CAS_N`, `CKE0/1`, `CS_N0/1`, `DQM0..DQM3`, `RAS_N`, `WE_N`

## 10. `UHSIF` (49) and `SERDES` (4) claimed nothing

`Disable`/`Enabled` with no signals, so all 49 ports and all four SerDes differential pads were
stranded - even though those two are the reason the dedicated-pins file exists.

## 11. `ADC`, `ADC2`, `CMP`, `OPA`, `HSADC` (the report)

* **`ADC1` offered 2 of its 16 channels** (`Channel 0 (IN0)` and `Channel 4 (IN4)`) and
  **`ADC2` had no `signal_pins:` at all** - it carried the generator's "holds no pin on any
  package" note. They share the same sixteen pads: the DS resource table has ONE
  `ADC_IN0~IN15` row ticked under each ADC, Table 2-2-1 is a single "ADC Pin functions" table
  with no ADC1/ADC2 split (unlike Table 2-2-3, which does split DAC1/DAC2), and RM ch.11 says
  "The conversion channels of ADC1 and ADC2 should not overlap at the same moment" - which
  only means something if they draw on one channel space. All 16 now, plus `IN16`
  (temperature sensor) and `IN17` (VREFINT) as named channels with no pad, which is how
  CH32V006 writes its Vrefint channel.
* **`CMP` had an output and no inputs.** RM ch.35's feature list is "CMP input pin selectable",
  and Table 2-2-22 gives P0/P1/P2 and N0/N1/N2. `CMP_P2` is `OPA1_OUT` and `CMP_N2` is
  `DAC1_OUT` - internal routes, not pads - so they are choices that name no signal, with the
  internal path in the label.
* **`OPA` offered only `Disable`/`Enabled` per unit.** Table 2-2-21 gives two pads for each of
  the three connections per unit, so it is now nine rows (`OPA1 positive input` -> `P0`/`P1`,
  and so on), which is CH32X035's `Positive input`/`Negative input`/`Output` shape.
* **`HSADC`** had no channel row; Table 2-2-2 gives `IN0..IN6`, all on pads.

## 12. `CMP`'s analog inputs were dropped by the generator, not by the datasheet

`CMP` was missing from `SPEC` in `gen_h417_dedicated_pins.py`. `CMP_OUT` carries an AF code so
the AF parser found it; `CMP_P0/P1` and `CMP_N0/N1` are analog pad functions with no `(AFn)`
marker, so nothing collected them. One missing dict key, and the comparator lost every input.

## 13. `SDRAM_CS_NO` - a letter O in the datasheet split one chip select in two

It appears **exactly once** in the whole source markdown, on PC2's row. Table 2-2-15 says:

    SDRAM_CS_N0   PC2(AF12), PC4(AF12), PD6(AF3), PE3(AF9)

So `CS_N0` and `CS_NO` are one signal - and the file had both, each holding part of it, so the
engine would report no conflict between two names for one chip select. Same failure the
remap-suffix convention caused on SDMMC, from a different cause. Normalised in `SIGNAL_FIX`;
there is no `CS_O` in the datasheet.

**The first fix for this was itself the merge bug again.** `groups[g][sig] = entries` REPLACES,
so mapping two names onto one key threw away the first one's pins - `CS_N0` came out with only
PC2 and lost PC4/PD6/PE3, i.e. worse than before. It is now a union, and the note in `MERGE`
about exactly this mistake is why it was caught.

## 14. `emit_peripheral()` silently dropped `type:`

The generator wrote `- name: …` and `choices:` and never `type:`, so `type: checkboxes` was
discarded. That is not cosmetic: a checkbox row became a single-choice row, and the engine's
default moved from "nothing ticked" (`new Set(def ? [def.name] : [])`) to `choices[0]`, which
for a channel list is a real pin. A freshly loaded project therefore read as ADC1 enabled with
channel IN0 selected, and two ADCs then collided on PA0. The `settings` guard above it could
not catch this: every name in it was valid.

## 15. Also unreachable, now fixed

`QSPI1`/`QSPI2` `SCSXN` + `SIOX0..SIOX3` (10 pads), `SDMMC` `SLVCK`/`STR`/`STS`, `DVP`
`D10`/`D11` (RM 29.4.1 `RB_DVP_MSK_DAT_MOD`: "00: 8-bit; 01: 10-bit; 1x: 12-bit" - the 12-bit
mode was simply missing), `ETH` `PHY_LED0..4` + `PPS`, `LPTIM1/2` `OC`, `I2C3`/`I2C4` `SMBA`
(all four I2Cs have an SMBA pad, so all four do SMBus), `TIM8` `BKIN2` (Table 2-2-4; TIM1 is
hand-written and already had it), and `RTC`'s wakeup output, which was a choice that named no
signal.

## The gate

`tests/completeness.test.js` now asserts, for **every real part**, that every signal a
peripheral routes is named by some setting choice - with `codegen.skip_signals` exempt, because
those pins are claimed by the debug interface or by `clock.hse_*` and no setting may name them.
All six parts are clean at 0. It was shown to bite: removing the signal name from HSADC's `IN6`
channel produced `CH32H417 HSADC: 1 of 7 routed signal(s) no setting names, so they cannot be
assigned: IN6`, and restoring it went green.

A planted break that only ADDED a settings row proved nothing, and is worth recording: the
original `Channels` row was still there naming all seven signals, so the data was still
complete and the test was right to pass. The plant has to remove the reachability, not the row.

## The four USB controllers: three of them held no pin at all (2026-09-12)

The human's report was that picking any USB mode claimed no pins. It was right, and it was
three of the four controllers. `USBFS`, `USBHS` and `USBSS` each offered
`Mode: [Disable, Device, Host]` with **no signal behind any choice**, routed nothing, and
carried the generated note *"This peripheral holds no pin on any package; it is configured
through its own registers and the clock tree only."*

That sentence was false for all three, and the datasheet says so in its own signal-first
tables — the same tables the SDMMC and UHSIF work already used:

| Controller | Source | Pads |
|---|---|---|
| `USBFS` | DS Table 2-2-18 | `OTG_DP` PA12, `OTG_DM` PA11, `OTG_VBUS` PA9, `OTG_ID` PA10 |
| `USBHS` | DS Table 2-2-19 | `USBHS_DP` PB8, `USBHS_DM` PB9 |
| `USBSS` | DS Table 2-1-1 | `SSTXB`, `SSTXA`, `SSRXB`, `SSRXA` — pin type `USB3.0` |
| `USBPD` | DS Table 2-2-17 | `CC1` PB3, `CC2` PB4 — **the one that was already modelled** |

DS Table 2-1-1 agrees with 2-2-18 and 2-2-19 pin for pin, and writes those functions
**first in the row with no `(AFn)` code**, because the transceiver is hard-wired to the pad
rather than selected through `GPIOx_AFR`. That is why all three are now in
`codegen.skip_signals`: the pins are **claimed**, so the conflict engine sees them, and the
generator writes no `GPIO_Init` and no `GPIO_PinAFConfig` for them.

**The vendor's own driver is the authority for that, not an argument.**
`EXAM/IAP/USB_UART/CH32H417_APP/Common/USB/ch32h417_usbfs_device.c:54-70` — `USBFS_RCC_Init()`
enables `RCC_HBPeriph_OTG_FS` and the GPIOA *clock*, and configures no pin at all.
`ch32h417_usbhs_device.c` contains no GPIO call of any kind.

### Four things this turned up that were not the reported defect

1. **`VBUS` and `ID` are a separate row, on purpose.** Neither source says which *role*
   requires them: the DS lists all four USBFS pins under one "Optional pin" column and RM
   ch.26 calls On-The-Go support *"an optional feature in the OTG_FS controller's physical
   layer"*. Inferring "a host needs VBUS" from general USB knowledge is the
   family-is-not-a-citation move this repo bans, so `Mode` carries the three roles RM ch.26
   names (device-only, host-only, dual-role) and an `OTG pins` checkbox row carries the two
   optional pads. Folding them into `Mode` would leave one of the two unclaimable — the same
   defect one level down.

2. **`USBHS` shares the debug pads, and the file was hiding it.** DS Table 2-1-1 spells PB8
   `SWCLK/USBHS_DP/…` and PB9 `SWIO/SWDIO/USBHS_DM/…`, and `SYS` routes SWCLK/SWIO to exactly
   those two. Enabling USB high-speed while the 2-wire debug port is on is a genuine conflict
   on silicon; the conflict engine now reports it on both pins instead of the data pretending
   the controller has no pads. `tests/h417_usb.test.js` asserts both directions.

3. **The coverage parser could not see a dedicated-pad row.** `SSTXA`/`SSTXB`/`SSRXA`/`SSRXB`
   are typed `USB3.0` in the pin table and the four Ethernet MDI pads are typed `ETH` —
   neither is in the `I/O/A/P/FT` alphabet the parser knew, so those eight rows were never
   anchored and their names were read as **functions of the power pad above them** (`VSS
   SSTXA`, `VDD12A SSRXA`). A part now declares its own pad types in
   `data/coverage/CH32H417.yaml` under `pin_types:`. This is the same class as every other
   parser defect on this part: the table was right and the reader was wrong.

4. **A validator warning was saying something untrue.** `signal_pins` with no `af:` warned
   "codegen will not guess an AF code and emits a TODO instead" — correct for a muxed pin,
   false for a pad in `codegen.skip_signals`, where the emitter skips it by design. The
   warning now respects `skip_signals`, which also silences the two `SYS` and two `RCC`
   warnings this file has carried since it landed. They were never gaps.

### Evidence

`--strict` exits 0 on `CH32H417_QFN128_full.wchproj` in both formats, and that fixture now
enables USBFS dual-role with **both** OTG pads and USBSS device — so the compile gate builds
generated C that claims eight USB pads, four of which are not spelled `Pxx`. The generated C
names them in its "not configured here, by design" line, emits `RCC_HBPeriph_OTG_FS` and
`RCC_HBPeriph_USBSS`, and carries no TODO and no `#error`. USBHS is left out of that fixture
because PB8 is already I2C1_SCL there and the collision is real; it is covered on its own in
`tests/h417_usb.test.js`.

Coverage: **113 -> 104 open rows**. Planted breaks, both shown red before this landed:
dropping `DP` from one USBFS mode is caught by name by `tests/h417_usb.test.js`; dropping it
from all three is additionally caught by `validate_mcu.py` as a dead pad.

## LTDC: the output width is wiring, "8-bit" is a frame-buffer format, and the spare lines are yours (2026-09-12)

The human asked two questions — *can the LTDC run in 8-bit mode, and if so can those pins be
used by other peripherals?* — and they have different answers that are easy to conflate.

### 8-bit exists, but not at the pad

| Where | Answer | Source |
|---|---|---|
| **Frame buffer (memory)** | **Yes.** `L8` (8-bit luminance, indexed through a 256-colour CLUT), `AL44` and `AL88` are all eight bits per pixel | RM 43.4.18, `LTDC_LxPFCR.PF[2:0]` = 101 / 110 / 111; `ch32h417_ltdc.h:200-208` |
| **Output pins** | **No.** There is no mode that narrows the bus | RM 43.4.5, `R32_LTDC_GCR`: four polarity bits, one enable, **bits [27:1] Reserved** |

The pixel format converter expands every input format to ARGB8888 before the blender — the
RM says so for ARGB1555 and ARGB4444 ("converts it into ARGB8888 by copying the high bits
and filling them into the low bits") — and the timing generator then drives a fixed 24-bit
parallel RGB port plus CLK/HSYNC/VSYNC/DE. **So an 8-bit format saves RAM and frees no pin.**

### Which means the width at the pad is a WIRING choice, and the spare lines really are free

A 16- or 18-bit panel is wired to the high bits of each channel and the low lines are left
unconnected. Nothing in the silicon reserves them: each is an ordinary pin that carries LTDC
only while its `GPIOx_AFRy` field selects LTDC's AF. The `Colour depth` setting is therefore
"how many lines did you wire", and it now offers the three standard wirings:

| Choice | Lines | Claims | Releases |
|---|---|---|---|
| `RGB888` | 24 | R0–R7, G0–G7, B0–B7 | nothing |
| `RGB666` | 18 | R2–R7, G2–G7, B2–B7 | **6** — R0–R1, G0–G1, B0–B1 |
| `RGB565` | 16 | R3–R7, G2–G7, B3–B7 | **8** — R0–R2, G0–G1, B0–B2 |

`RGB666` is new. Measured: with `RGB565` selected on QFN128 all eight released pads take a
manual GPIO output with **0 conflicts** and generated C carrying no `TODO` and no `#error`.

### The defect this turned up, and it was live

**Four pads were the default for two different LTDC signals at once.** `defaultSignalPin()`
takes the first option bonded on the package, and the file's order gave:

```
PA8  = R6 + B3      PA15 = R3 + CLK      PA6 = G2 + HSYNC      PA10 = B1 + B4
```

The conflict engine reported **nothing**, because it flags a pad only when the claims have
different OWNERS — and both of those are LTDC. One pad drives one bit, so simply switching
the display on produced a configuration the silicon cannot honour. It was worse on QFN68,
where five pads collided across twelve signals.

Fixed by **reordering** each signal's option list — no pin added, none removed, every AF code
untouched — so that the first bonded option is distinct. The order was solved as a bipartite
matching over the pins bonded on **all three** packages, so one order is collision-free
everywhere. A second constraint fell out of it for free: no default may sit on the debug pads,
and `B7` used to default to `PB9`, which is SWIO/SWDIO — enabling the display collided with
the debug port before the user touched anything. `B7` now defaults to `PD2`.

`tests/h417_ltdc.test.js` holds all of it, per package, and was shown red on a planted
collision (`R3` put back on `PA15`) before it landed.

### Still open, deliberately

The layer pixel format is **not selectable**. `LTDC_Layer_InitTypeDef.LTDC_PixelFormat` is
applied by `LTDC_LayerInit(LTDC_Layerx, &s)` — a struct filled once **per layer**, with the
layer handle (`LTDC_Layer1` / `LTDC_Layer2`) as an argument. `codegen.init_structs` maps a
struct to one function and `codegen.periph_handle` maps a peripheral to one handle, so
neither can express it today, and a `params:` entry written now would emit a TODO and fail
the `--strict` gate. It is on `TASKS.md` with the H417 `params:` work rather than guessed at.
