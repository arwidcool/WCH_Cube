# CH32X035 — extraction notes

Companion to `data/mcus/CH32X035.yaml`. Every fact below cites an EVT `file:line`, an RM
section or a DS table. Open questions are recorded as open questions, never as plausible
values — that is the round-4 rule and this part needed it more than once.

**Status: the file is PARTIAL and says so.** What is in, what is not, and why, is the last
section. A partial part beats a fake one.

## Why nothing may be carried over from CH32V006 by analogy

Eleven differences, each confirmed, each capable of breaking something that works today.
The first nine were in the round brief; the last two this extraction found.

| Fact | CH32X035 | CH32V005/V006 | Source |
|---|---|---|---|
| HSE | **none at all** | HSE + PLL | `grep -c HSE ch32x035_rcc.h` → 0 |
| Clock sources | one 48 MHz RC, SYSCLK 8/12/16/24/48 | HSI + HSE + PLL | EVT `system_ch32x035.c`:19-23 |
| GPIO ports | A, B, C | A, B, C, D | `ch32x035.h`:656-658 |
| Port width | **24 bits**, `uint32_t` | 16 bits | `ch32x035_gpio.h`:76-83 |
| Port C | **not contiguous, two holes** | contiguous | DS Table 2-1 |
| Remaps | 40 **named macros** + `GPIO_PinRemapConfig` | raw `AFIO_PCFR1` fields | `ch32x035_gpio.h`:88-125 |
| Clock domains | AHB / APB1 / APB2 | HB / PB1 / PB2 | `ch32x035_rcc.h`:46-70 |
| DMA channels | **8** | 7 | `ch32x035.h` `DMA1_Channel8_BASE` |
| NVIC vectors | **45**, EXTI grouped | 29 | `ch32x035.h` + startup |
| **GPIO modes** | **6 — NO OPEN DRAIN** | 8 | `ch32x035_gpio.h` `GPIOMode_TypeDef` |
| **Pull-down** | **not on every pin** | every pin | `ch32x035_gpio.h`, comment on `GPIO_Mode_IPD` |

### The two this extraction found, both caught by `verify_sdk_names.py`

**There is no open-drain on this part.** `GPIOMode_TypeDef` has exactly six members:
`GPIO_Mode_AIN`, `IN_FLOATING`, `IPD`, `IPU`, `Out_PP`, `AF_PP`. There is no
`GPIO_Mode_Out_OD` and no `GPIO_Mode_AF_OD`. I wrote both into `gpio.modes` out of habit,
copying the CH32V006 list, and the gate rejected them — which is precisely the argument
for having the gate: they are real, correctly spelled SPL names belonging to a different
chip, and nothing else in the repo would have noticed. **The GPIO table must not offer
either mode on this part.**

**Pull-down is a per-PIN capability here.** The header says so in a comment on the member
itself: `GPIO_Mode_IPD = 0x28, /* Only PA0--PA15 and PC16--PC17 support input pull-down */`.
No part in `data/mcus/` has ever had a pull that works on some pins and not others, and the
schema cannot express it yet. Recorded on the `input_modes` entry as `pins_note:` and
raised on the board. **Open:** the right schema. A `pins:` allow-list on the mode is the
obvious shape, but it should be agreed with AGENT-2 before it is filled.

## Pins and packages

The package tables were re-derived from DS Table 2-1 by `tools/extract_pins.py` and diff
to **0 differences** against the DS model table's own I/O column, on all seven packages:
LQFP64M 60/60, LQFP48 46/46, QFN28 27/27, QSOP28 26/26, QFN20 19/19, TSSOP20 18/18,
QFN12 11/11.

### The exact port shape, settled from the pin table

- **Port A: PA0–PA23, 24 pins, contiguous.**
- **Port B: PB0–PB21, 22 pins, contiguous.**
- **Port C: PC0–PC7, PC10–PC11, PC14–PC19 — 16 pins, TWO holes** (PC8–PC9, PC12–PC13).

`PC8`, `PC9`, `PC12` and `PC13` appear in no row of Table 2-1 and nowhere in the RM.
AGENT-4's 16:25Z correction — that port C has two holes rather than one — is confirmed,
and it is confirmed from the table rather than from a name count.

A round-3 board entry of mine said port C ran "PC0-PC7 then PC14-PC19", i.e. one hole.
That was wrong, and it was wrong because it came from reading rather than parsing.

### Two rows the PDF conversion destroyed

Declared in `data/sources/X035/Datasheets/CH32X035_pin_corrections.yaml`, printed in full
on every extractor run, and each certain from the rows immediately around it:

- **PB19** (DS:1809) lost one of its seven dashes — six cells and a tell-tale double
  space. PB16/17/18 are each LQFP64M-only and PB19 sits between PB18 at 39 and PB9 at 41.
- **PC3's second row** (DS:1706) lost its name line entirely. PC3 has two rows because its
  main function differs by package; the second is a bare run of cells followed straight by
  `RST/C1N0/C2N1/C3N1/A13`.

The PC3 correction was written before I found DS:2583, which states independently: *"The
RST function on pin PC3 is only available for the CH32X035 in the QSOP28 package and
TSSOP20 package."* That is the same conclusion from a different part of the document, and
it is the reason the correction is safe rather than merely plausible.

### Shorted pin pairs, and they depend on the package

DS notes 4–7. A pair shorted inside the package reaches the YAML as two names on one pin
number, which is how the conflict engine already treats CH32V006's PA1/PA6.

| Pair | Shorted on | Not on | Note |
|---|---|---|---|
| PC11 + PC16 | all except QFN20, QFN12 | QFN20, QFN12 | 4 |
| PC10 + PC17 | all except QFN20, QFN12 | QFN20, QFN12 | 4 |
| PB1 + PB5 | QFN28, QSOP28 | others | 5 |
| PA12 + PC14 | QSOP28 | others | 6 |
| PA13 + PC15 | QSOP28 | others | 6 |
| PA7 + PC7 | QFN12 | others | 7 |

**PC10 and PC11 have no column of their own in Table 2-1** — they exist only as the shorted
partners of PC17 and PC16. They are in `pins:` because they exist on the die.

Every one of those notes adds *"both IOs are prohibited from being configured as output
functions"*. **Open:** that is a per-pin capability the schema cannot express, exactly like
the pull-down constraint, and it is the same shape of problem. A shorted pair driven from
both ends is a short circuit, so this is not cosmetic.

DS note 4 adds that **in USB applications PC10 and PC11 must be floating inputs**. PC16 and
PC17 are the USB data pins, so that is a coupling between a peripheral being enabled and
two other pins' modes — the same shape as round 2's HSE coupling, and not expressible yet.

### Packages

- **QSOP28 added** to `data/packages/packages.yaml`: dual, 28 pins, pitch 0.635,
  body 9.9 × 3.9 (DS ch.4: *"QSOP28 3.9*9.9mm 0.635mm 25.0mil"*).
- **LQFP64M added, and it is dimensionally identical to LQFP64** — DS ch.4 says
  *"LQFP64M 10*10mm 0.5mm"*, which is exactly LQFP64's geometry. Kept as its own id
  because that is what the part's model table calls it; recorded here so nobody
  re-measures it. WCH's M suffix is a body/mould option, not a size.
- While checking those, three existing geometries turned out to disagree with both
  datasheets and were corrected: **QFN20, QFN28 and QFN32 had pitch 0.5 and QFN32 had body
  5×5**. CH32V006 DS ch.5 says *"QFN32 4*4mm 0.4mm"*, *"QFN20 3*3mm 0.4mm"*; CH32X035 DS
  ch.4 says *"QFN28 4*4mm 0.4mm"*. Both fields are informational and neither changes the
  drawing, but a wrong number is a number the next part copies.

## Clock

**No HSE and no PLL.** One internal 48 MHz RC. EVT's `system_ch32x035.c` offers exactly
five SYSCLK settings and every one is HSI: 8, 12, 16, 24, 48 MHz, with 48 the default
(lines 19-23).

`RCC_CFGR0` (RM v1.9 §3.4.2, offset 0x04, reset `0x00000050`) has **no `SW` field at
all** — there is nothing to switch between, so the register has no source mux. Only
`MCO[2:0]` at bit 24 and `HPRE[3:0]` at bit 4 are user fields; everything else is Reserved.

Two things worth not rediscovering:

- **HCLK comes out of reset at SYSCLK/6 = 8 MHz.** HPRE's reset value is `0101b`, which
  the register's `0x00000050` reset value confirms.
- **MCO offers only two sources** — SYSCLK (`100`) and HSI (`101`), everything else
  meaning no output. That is the no-HSE shape showing up a second time.

MCO is on **PB9** (DS Table 2-1: `PB9 CK1/T1C1/MCO`).

## Interrupts

**45 vectors**, and the two EVT sources agree on every single one: `IRQn_Type` in
`ch32x035.h` and the `.word` table in `startup_ch32x035.S` give the same number, the same
name, a handler for every enum entry and an enum entry for every handler, with nothing on
one side only. That is a stronger cross-check than CH32V006 got.

**The round-4 brief says 47. It is 45.** Counted twice, from two independent files.

**There is no RCC vector.** Number 19 is a gap in the enum and a `.word 0` in the table,
where CH32V006 has `RCC_IRQn = 19`. *Every family has an RCC interrupt* is exactly the kind
of assumption this part exists to break, and it is a permanent absence rather than a gap in
this extraction.

**The EXTI vectors are grouped**, so each carries an inclusive `lines: [first, last]`:

| Vector | Number | EXTI lines |
|---|---|---|
| `EXTI7_0_IRQn` | 20 | 0–7 |
| `EXTI15_8_IRQn` | 40 | 8–15 |
| `EXTI25_16_IRQn` | 41 | 16–25 |

`ch32x035_exti.h` defines **30 lines**, not 26. Lines 26–29 are internal events — PVD,
auto-wake-up, USBFS wake-up and USBPD wake-up — each with its own vector, so they are not
covered by the grouped three. Lines 24 and 25 are PC18 and PC19 and are marked *"(SDI on)"*.

### The PFIC priority scheme is NOT CH32V006's — checked, and different

The brief was right that this must not be carried across by analogy, and it turned out to
matter. From **this** manual's PFIC chapter (RM v1.9 §7.5.2.37, `PFIC_IPRIORx`):

| | CH32X035 (QingKe V4C) | CH32V006 (QingKe V2A) |
|---|---|---|
| Priority control bits | **[7:5] — three** | [7:6] — two |
| Reserved, write invalid | [4:0] | [5:0] |
| Priority levels | **8** | 4 |
| Max nesting depth | 2 | 2 |

So a priority spinner that hardcodes either part's range is wrong on the other. With no
nesting configured there are no preemption bits and all three are plain priority (0–7);
with 2-level nesting *"bit 7 is the preemption bit"*, leaving [6:5] as sub-priority (0–3).
*"The smaller the priority value, the higher the priority."*

As on CH32V006, **where the nesting depth is selected is not in this register**, and no
register write is claimed for the switch itself — it is a labelled choice and nothing more.

## The ADC is not CH32V006's, in three ways

The `params:` for USART1-4, SPI1, I2C1 and TIM1/2/3 were **ported** from CH32V006 — the
init structs are member-for-member identical between the two families — and then re-checked
against the X035 headers. That is acceptable only because there is a gate behind it, and
the ADC is what the gate caught.

**Sample times are named and valued completely differently.** CH32V006 spells them
`ADC_SampleTime_CyclesMode0..7` and means 3.5 to 239.5 cycles. CH32X035 spells them
`ADC_SampleTime_4Cycles` … `_11Cycles` and means exactly that — **four to eleven**, one per
code. All eight ported options were rejected by `verify_sdk_names.py`. A much shorter
range, and nothing about the CH32V006 names would have hinted at it.

**`ADC_InitTypeDef` has two members CH32V006's does not** — `ADC_OutputBuffer` and
`ADC_Pga`. **Neither is modelled, and that is deliberate.** The header documents
`@ref ADC_OutputBuffer` and `@ref ADC_Pga` and then **defines no such macro groups**;
`ch32x035_adc.c` ORs both straight into `ADC_CTLR1`; and no example anywhere in the 2 239-file
EVT drop assigns either one. So the field names are known and the legal values are not.
**Open:** find the values in the RM's ADC chapter, or leave them out. Offering them with
invented macro names is exactly what this round bans.

Note the asymmetry, because it decides how much "port it and let the gate arbitrate" is
worth: a member **this part lacks** shows up as a gate error, loudly. A member **this part
has and the other does not** shows up as *nothing at all* and has to be found by reading
the struct. The gate is a backstop for porting, not a substitute for reading.

**Low power:** `ch32x035_adc.h` exposes nothing for it either — no struct member, no
function — so the same `sdk_none: true` treatment as CH32V006, re-checked against this
header rather than assumed to carry across.

## DMA: eight channels, and a request map the conversion half-destroyed

RM 9.2: *"The DMA controller provides 8 channels"*, and `ch32x035.h` defines
`DMA1_Channel1_BASE` … `DMA1_Channel8_BASE`. CH32V006 has seven.

**The request-mapping table is one of the places the PDF conversion did real damage.**
The peripheral rows survive but the column positions are gone, so
`USART1 USART1_TX USART1_RX` still says which requests exist and no longer says which
channels they sit on. Reading a channel number off that would be a guess.

What is in the file comes from **WCH's own EVT examples**, which name the channel in code
and usually in a comment beside it:

| Request | Channel | Evidence |
|---|---|---|
| ADC1 | 1 | `EXAM/ADC/ADC_DMA/User/main.c` |
| SPI1_RX | 2 | `SPI/SPI_DMA/.../main.c:221` `DMA_Rx_Init(DMA1_Channel2, &SPI1->DATAR)` |
| SPI1_TX | 3 | `SPI/SPI_DMA/.../main.c:220` `DMA_Tx_Init(DMA1_Channel3, &SPI1->DATAR)` |
| USART3_TX | 2 | `USART/USART_DMA/.../main.c:123` `/* USART3 Tx */` |
| USART3_RX | 3 | `USART/USART_DMA/.../main.c:124` `/* USART3 Rx */` |
| USART2_RX | 6 | `USART/USART_DMA/.../main.c:122` `/* USART2 Rx */` |
| USART2_TX | 7 | `USART/USART_DMA/.../main.c:121` `/* USART2 Tx */` |
| I2C1_TX | 6 | `I2C/I2C_DMA/.../main.c:192` `DMA_Tx_Init(DMA1_Channel6, &I2C1->DATAR)` |
| I2C1_RX | 7 | `I2C/I2C_DMA/.../main.c:215` `DMA_Rx_Init(DMA1_Channel7, &I2C1->DATAR)` |

Those also reveal something useful about the damaged table: **the RM lists each
peripheral's requests left to right in channel order.** `USART2 USART2_RX USART2_TX` is RX
then TX and the example confirms 6 then 7; `USART3 USART3_TX USART3_RX` is TX then RX and
the example confirms 2 then 3. So the row *order* survived and only the column *positions*
were lost — which is why the rest is recoverable in principle.

**Open:** `USART1_TX/RX`, `USART4_TX/RX`, and every TIM1 and TIM2 request. The most likely
route is the RM's original PDF or the DMA chapter's per-peripheral prose; failing that, a
WCH example that uses them. Not guessed.

## Not modelled yet, and why

The pin-bearing peripherals need their remap tables derived from **DS Table 2-3**, which is
~470 lines of abbreviated per-pin tokens (`T2C1_2`, `CTS2_1`, `O1N2`, `A13`) with the remap
index encoded as the suffix after the underscore (DS note 2: *"the value after the
remapping function underline indicates the configuration value of the corresponding bit in
the AFIO register"*). That decode needs its own parser and its own second pass, and it is
not something to half-do.

**In:** SYS, RCC, DMA1, IWDG, WWDG, USBFS, USBPD.

**Out, with their vectors deliberately omitted rather than given invented owners:**
ADC1, SPI1, I2C1, USART1–4, TIM1, TIM2, TIM3, PWR, FLASH, EXTI, PIOC, OPA, AWU.
Twenty-five of the 45 vectors are waiting on those peripherals. `validate_mcu.py` refuses a
vector whose owner does not exist and is right to; the alternative — a vector with no owner
— would file USART1's interrupt under System Core, which is worse than an honest gap.

Also absent and worth naming:

- **TouchKey.** The DS advertises 14-channel TouchKey on every variant, and **the EVT
  package ships no `tkey` header** — 21 headers, none of them TouchKey. On CH32V006 the
  answer turned out to be that TouchKey is a *mode of the ADC* rather than a peripheral
  (`TKey1` is `#define`d to `ADC1_BASE`). **Open:** whether the same holds here. Do not
  model it until that is checked against `ch32x035_adc.h`.
- **CH32X033F8P6** is in the same DS model table and is **not** a variant of this file. It
  has its **own pin table** (DS Table 2-2), so its pinout differs; it belongs in its own
  `CH32X033.yaml`, most likely via `inherits: CH32X035` once Table 2-2 is parsed. Note that
  Table 2-2 immediately follows Table 2-1 with no end marker between them, which is how
  `extract_pins.py` once read 26 rows of CH32X033 data as CH32X035 pins.
- **USBFS has two handles at one base address** — `USBFSD` for device and `USBFSH` for host
  (`ch32x035.h`:676-677, both at `USBFS_BASE`). `codegen.periph_handle` can hold only one,
  and Device is named because it is the common case. **Open:** how the host case is
  expressed. It is a real modelling question, not an oversight.
- **DS note 3 is a silicon-revision caveat**, not a package or variant fact: ADC channels
  3, 7, 11 and 15 and the I2C functions *"are not available for products with a lot number
  with a penultimate 5 digit of 0"*. It cannot be expressed per package or per variant and
  we cannot know which lot a user has, so it is recorded here and must be neither silently
  dropped nor silently applied.
