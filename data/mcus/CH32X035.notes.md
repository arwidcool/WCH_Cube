## Why nothing may be inherited from CH32V006 by analogy

Every row below differs from the V00x family. This is the single most important page in
this file: the two parts look like siblings and are not.

| Fact | CH32X035 | CH32V005/V006 | Source |
|---|---|---|---|
| GPIO ports | **A, B, C only** | A, B, C, D | `ch32x035.h`:656–658 |
| Port width | **24 bits** — `GPIO_Pin_0..23` | 16 bits | `ch32x035_gpio.h` |
| Port is contiguous? | **No** — PC is 0–7 then 14–19 | yes | DS Figure 1-1 |
| Pins per port | PA0–PA23, PB0–PB21, PC0–PC7 + PC14–PC19 | PA/PC/PD 0–7 | DS Figure 1-1 |
| Clock enable fn | `RCC_APB2PeriphClockCmd` | `RCC_PB2PeriphClockCmd` | `ch32x035_rcc.h` |
| Clock enable macro | `RCC_APB2Periph_GPIOx` | `RCC_PB2Periph_GPIOx` | same |
| GPIO speeds | one: **`GPIO_Speed_50MHz`** | one: `GPIO_Speed_30MHz` | `ch32x035_gpio.h`:25 |
| `RCC_ClocksTypeDef` | **no** `ADCCLK_Frequency` | has it | `ch32x035_rcc.h` |
| Extra peripherals | USB, USBPD, AWU, PIOC | none of them | EVT header list |
| TouchKey header | none — it is an ADC mode | none either | EVT header list |

**The two that will bite code rather than data:** a 24-bit port breaks any pin-name
regex, bit mask or package table that assumes 16, and a port with a hole in it breaks
anything that iterates a range. `tools/extract_pins.py` carried the first of those
assumptions itself until round 3 — see its header comment.

`data/firmware/platformio.ini` defines **one** environment today, `CH32X035G8U6`, so only

**CH32X033 is a different part and belongs in its own file, not this one.** The DS
documents it in Table 2-2 with fewer package columns, which is exactly the trap
`tools/extract_pins.py` fell into: with no end marker between the tables it read 26 rows
of CH32X033 data as CH32X035 pins. Fixed, but worth knowing before anyone points a
parser at this datasheet.

## Pin table extraction status

`tools/extract_pins.py` with `--pin-re "P[A-C]\d{1,2}"` and the seven package columns in
DS order (`LQFP64M,LQFP48,QFN28,QSOP28,QFN20,TSSOP20,QFN12`) currently parses:

| Package | Parsed | DS I/O count | Short by |
|---|---|---|---|
| LQFP64M | 56 | 60 | 4 |
| LQFP48  | 44 | 46 | 2 |
| QFN28   | 24 | 27 | 3 |
| QSOP28  | 23 | 26 | 3 |
| QFN20   | 17 | 19 | 2 |
| TSSOP20 | 15 | 18 | 3 |
| QFN12   |  9 | 11 | 2 |

Five rows are reported ambiguous rather than guessed at, and **all five are now
understood** — they are the shorted USB pins and one dropped dash:

- **PB19** (DS line ~1809) reads `40 - - - -  - PB19`: six cells where seven are needed.
  The PDF dropped one placeholder. Its neighbours PB16/PB17/PB18 all read
  `<n> - - - - - -`, so PB19 is LQFP64M pin 40 only.
- **PC16 / PC11** and **PC17 / PC10** are split across several lines each, because the
  DS gives the shorted partner its own row with no package cells. See the next section —
  they are not missing data, they are aliases.

The remaining count gap is those aliases plus the split rows; nothing suggests a row the
parser cannot reach once the aliases are modelled.

## Shorted pin pairs — and they are PER PACKAGE

This part has more of them than CH32V006 and, unlike CH32V006, **which pairs are shorted
depends on the package**. The engine already models a shorted pair as one physical pin
carrying two names (`packages:` maps a number to a *list*), so this fits — but it has to
be written per package table, not once.

From the DS notes under Table 2-1:

| Pair | Shorted on | Not shorted on | Note |
|---|---|---|---|
| PC10 + PC17 | every model **except** F8U6 (QFN20) and D8U6 (QFN12) | F8U6, D8U6 | 4 |
| PC11 + PC16 | every model **except** F8U6 and D8U6 | F8U6, D8U6 | 4 |
| PB1 + PB5 | G8U6 (QFN28), G8R6 (QSOP28) | others | 5 |
| PA12 + PC14 | G8R6 (QSOP28) | others | 6 |
| PA13 + PC15 | G8R6 (QSOP28) | others | 6 |
| PA7 + PC7 | D8U6 (QFN12) | others | 7 |

Note 10's PA7 + PB0 pair is **CH32X033F8P6**, a different part, and must not be applied
here.

Two consequences for the data beyond the pin numbers:

- Every one of these notes says *"both IOs are prohibited from being configured as output
  functions"*. That is a real per-pin capability, not a warning to put in prose — a
  shorted pair driven from both ends is a short circuit. Whatever key expresses it, the
  UI must not offer an output mode on those pins.
- Note 4 adds that **in USB applications PC10 and PC11 must be floating inputs**, which
  is the reset default. PC16/PC17 are the USB data pins (`UDM` / `UDP` in the DS default
  alternate-function column), so this couples to the USB peripheral being enabled.

## Other per-pin facts the DS states outright

- **PC17 is the BOOT detection pin** (note 8): high at power-up sends the chip into the
  BOOT area. Same class of fact as CH32V006's RST_MODE option byte — it constrains what
  the pin may be used for, and belongs where the conflict engine can see it.
- **PC16 needs an external pull-up for I2C** (note 9).
- **Note 3 is a silicon-revision caveat, not a pin fact**: ADC channels 3, 7, 11 and 15
  and the I2C functions *"are not applicable to products with a lot number with the
  penultimate bit 5 being 0"*. This cannot be expressed per package or per variant and
  should be recorded as a peripheral-level note rather than silently dropped or silently
  applied.
