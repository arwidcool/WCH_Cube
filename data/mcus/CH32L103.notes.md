# CH32L103 — extraction notes

Sources: `data/sources/l103/datasheets/CH32L103DS0.md` (Datasheet V2.1) and
`CH32L103RM.md` (Reference Manual V2.2), plus the EVT package under
`data/sources/l103/evt/` (lower-case folder names, the V003 spelling — the tools
search recursively and case-insensitively, so it works as-is and `codegen.sdk.evt`
cites the path as it exists today, which is what keeps the path gate green).

**Status: NOT EXTRACTED. There is no `data/mcus/CH32L103.yaml`, and this file says
why.** Everything below is established from the sources and cited; the pin tables are
the blocker and are recorded in §4.

Nothing here is inferred from a sibling part. Where the sources are silent, that is
written down as an open question rather than filled in by analogy.

## 1. What is established, with citations

### Identity and variants — DS "Model / Resource" table (CH32L103DS0.md:111-160)

| Variant | Package | Pins | Flash | SRAM | GPIO | Temp |
|---|---|---|---|---|---|---|
| CH32L103C8T6 | LQFP48 | 48 | 64K | 20K | 37 | -40~85 |
| CH32L103K8U6 | QFN32 | 32 | 64K | 20K | 31 | -40~85 |
| CH32L103K8U7 | QFN32 | 32 | 64K | 20K | 31 | -40~105 |
| CH32L103G8R6 | QSOP28 | 28 | 64K | 20K | 26 | -40~85 |
| CH32L103F8U6 | QFN20 | 20 | 64K | 20K | 19 | -40~85 |
| CH32L103F8P6 | TSSOP20 | 20 | 64K | 20K | 16 | -40~85 |

- The GPIO column above is the DS's own `GPIO port number` row and is the check the
  parser diffs against (§4). It is **not** the pin count.
- "L103K8U6, K8U7 and F8U6 have built-in Type-C specification-defined controllable Rd
  pull-down resistors of about 5.1kΩ" — DS:156. "K8U7 shares identical performance
  characteristics except for a broader operating temperature range" — DS:158.
- Core: QingKe RISC-V **V4C**, RV32IMA(F)C, 96 MHz max — DS "Core"/"CPU main frequency".
- Package geometries for all five packages **already exist** in
  `data/packages/packages.yaml` (LQFP48, QFN32, QSOP28, QFN20, TSSOP20), so this part
  needs no change to the geometry library.

### CH32M103 is a different part — DS Table 2-1-2 (CH32L103DS0.md:2595)

`CH32M103G8R6` shares the QSOP28 package with L103G8R6 but **not the pinout**: 18 GPIO
against 26 (DS model table), a 3-phase gate driver, and its own pin table. It is
therefore a separate `data/mcus/` file, the same call that kept `CH32X033F8P6` out of
`CH32X035`. Not extracted here.

### Ports — `evt/EXAM/SRC/Peripheral/inc/ch32l103.h:771-774`

Ports **A, B, C and D**, all four at `PB2PERIPH_BASE`. This is the CH32V00x shape
rather than CH32X035's three ports — but see §4 before assuming 16-bit widths; the
width is not yet read off the header.

### Clock enables — `ch32l103_rcc.h:120-124`, `:200-202`

```c
#define RCC_PB2Periph_AFIO   ((uint32_t)0x00000001)
#define RCC_PB2Periph_GPIOA  ((uint32_t)0x00000004)
...
void RCC_HBPeriphClockCmd(uint32_t RCC_HBPeriph, FunctionalState NewState);
void RCC_PB2PeriphClockCmd(uint32_t RCC_PB2Periph, FunctionalState NewState);
void RCC_PB1PeriphClockCmd(uint32_t RCC_PB1Periph, FunctionalState NewState);
```

**Domains are HB / PB2 / PB1**, which is the CH32V00x spelling with a `PB2` (not
`APB2`), and there is no `RCC_PB2Periph_` → `RCC_APB2Periph_` rename here. This
matters because it is the field that has already been wrong once in this repo:
`codegen.gpio_clock.fn` must be `RCC_PB2PeriphClockCmd`, not `RCC_APB2PeriphClockCmd`.

### GPIO — `ch32l103_gpio.h:25-27`, `:33-40`

**Three speeds**, so the speed control is a real choice on this part for the first time
in this repo:

```c
    GPIO_Speed_10MHz = 1,
    GPIO_Speed_2MHz,
    GPIO_Speed_50MHz
} GPIOSpeed_TypeDef;
```

**Eight modes**, the full set — including the two open-drain modes CH32X035 does not
have:

```c
    GPIO_Mode_AIN = 0x0,
    GPIO_Mode_IN_FLOATING = 0x04,
    GPIO_Mode_IPD = 0x28,
    GPIO_Mode_IPU = 0x48,
    GPIO_Mode_Out_OD = 0x14,
    GPIO_Mode_Out_PP = 0x10,
    GPIO_Mode_AF_OD = 0x1C,
    GPIO_Mode_AF_PP = 0x18
} GPIOMode_TypeDef;
```

`gpio.speeds` must therefore have **three** entries and `gpio.modes` **five**, with the
three input modes under `input_modes`. That is CH32V006's shape, and unlike CH32X035 it
is the *correct* shape here rather than a copy — but it must be written from these lines,
not copied from CH32V006, because the enum values are what a sibling copy gets wrong.

### Remaps — macro style, `ch32l103_gpio.h:82-128`, applied by `:170`

`GPIO_PinRemapConfig(uint32_t GPIO_Remap, FunctionalState NewState)` — so
`codegen.remap.style: macro`, exactly like CH32X035. The macros encode the register in
bits[31:30] (`11b` = PCFR1[15:0] **and** PCFR2[26:16], `00b` = PCFR1, `01b` = PCFR2) and
the field value below, which the SDK decodes. Named groups, from the header:

| Peripheral | Macros |
|---|---|
| SPI1 | Partial1, Partial2, Full |
| I2C1 | Partial1, Full |
| USART1 | Partial1, Partial2, Partial3, Partial4, Full |
| USART2 | Partial1, Partial2, Full |
| TIM1 | Partial1..5, Full |
| TIM2 | Partial1..5, Full |
| USART3 | Partial, Full |
| TIM3, TIM4 | one each |
| CAN1 | Remap1, Remap2 |
| USART4, LPTIM | one each (PCFR2) |
| PD01 | one (PD0/PD1 ↔ OSC_IN/OSC_OUT) |
| SWJ_Disable | one — **note:** this is not a pin route, it disables the SDI debug port |

The RM gives each field's pin mapping in prose (`CH32L103RM.md:6310` onward for PCFR1,
`:6731` for PCFR2) and is the authority for it. Two facts from there that a sibling copy
would get wrong:

- **`TIM1_RM` and `TIM2_RM` are 3 bits, not 2** — `{TIM1_RM_H, TIM1_RM}` with the high
  bit in PCFR2 (`CH32L103RM.md:6420`, `:6449`). Six legal values each, which is why the
  header has six macros.
- **`GPIO_Remap_SWJ_Disable` must not be offered as a pin route.** It turns the debug
  interface off; the app models the debug interface as the `SYS` peripheral's setting,
  and a second control for the same thing is how two mechanisms start disagreeing.

### NVIC — `ch32l103.h:37` onward

Per-vector EXTI on this part: `EXTI0_IRQn` = 22 through `EXTI4_IRQn` = 26 individually,
then `EXTI9_5_IRQn` = 39 and (further down) `EXTI15_10_IRQn`. So EXTI lines 0-4 are one
vector each and 5-15 are grouped in two — a third shape again, neither CH32V006's single
`EXTI7_0` nor CH32X035's three grouped vectors. Also `TAMPER_IRQn` = 18, `RTC_IRQn` = 19
and `RCC_IRQn` = 21, none of which CH32V006 has. The full list must be taken from this
enum and the startup table, both mechanically — `irqn` and `handler` are different names
and the vendor is inconsistent between them.

## 2. The DS is mangled, and in one way that stops the extraction

`docs/ADDING-A-PART.md` warns that DS conversions are mangled and that a parser plus a
second-pass diff is what fixes it. That is true here, and one form of the damage is
worse than CH32X035's:

1. A pin name is split **mid-token** across lines: `V`+`BAT` = VBAT,
   `PC13-`+`TAMPER-RTC` = PC13-TAMPER-RTC, `OSC_OU`+`T` = OSC_OUT, `V`+`SSA`,
   `V`+`DDA`.
2. A row's five pin numbers can themselves be split across lines.
3. A trailing footnote marker is glued to the name (`PC13-TAMPER-RTC(2)`).
4. **The conversion drops the `-` placeholder cells.** A row for a pin absent from a
   package has FEWER than five numbers:

   ```
   ## 19 17 23 34 PA13      <- four numbers. Which package is absent?
   ```

That fourth one is the blocker. With a placeholder missing, the columns can no longer be
told apart **by position**, and the row also fails any "five number tokens in a row" test,
so it is silently read as a continuation of the row above and two pins are lost at once.

Evidence it is real and not a parser artefact: **LQFP48 pin 34 is missing from the
reconstructed table, and PA13's row shows it at 34.** The same happens at pin 45.

CH32X035 hit the identical corruption and the fix there was to recover the lost cells
**from the original PDF by word position**
(`data/sources/X035/Datasheets/CH32X035_pin_corrections.yaml`). **This drop's PDFs are in
the repo now** — `data/sources/l103/datasheets/CH32L103DS0.PDF` and `CH32L103RM.PDF`,
added after this section was written — so the same recovery is available, and it is the
**last resort** of the rule in `data/sources/README.md` ("Read the markdown first. The PDF
is the last resort."): the markdown is read first, and the PDF is opened only when the
conversion demonstrably cannot answer — which is the case here, and is re-checked on every
run of `tools/recover_l103_pins_from_pdf.py` rather than assumed.

**But there is a second source in the file, and it is the way through.** DS §2.1
"Pinouts" (`CH32L103DS0.md:1540` onward) is the package-arrangement figures, one per
package, and the conversion kept their text: pin numbers and pin names are both present,
in diagram order, e.g. for QFN32 (TSSOP20/QFN20/QSOP28/LQFP48 follow the same shape):

```
## 18 ## 19 ## 20 ## 21 ## 22 ## 23 ## 24 ## 2526272930313228
## 17 ## CH32L103K8U ## PC14/OSC32IN ## PC15/OSC32OUT ## PA0/WKUP/ADC0 ...
```

It is mangled too (`2526272930313228` is eight pin numbers concatenated), and the figure
layout that says which label sits beside which pin is lost, so it cannot be read by a
naive parser either. But it was produced from a **different part of the document** than
Table 2-1-1, so it is an independent derivation of the same fact — which is exactly what
`CH32X035_pin_corrections.yaml` is: a second, weaker source used to settle the rows the
first one destroyed. Note the QFN32 sequence above is `25,26,27,29,30,31,32,28`: **24 is
absent from it**, which is a lead on one of the lost rows rather than a fact.

## 3. What the parser says today

`tools/extract_l103_pins.py` (new, additive) reads Table 2-1-1 on a flat token stream and
self-checks two ways: pin numbers must run 1..N with no gaps (pin 0 allowed as the exposed
pad), and each package's GPIO count must equal the DS model table's own `GPIO port number`.

```
rows parsed: 46
  TSSOP20   20 rows,  12 GPIO  (DS says 16)
  QFN20     21 rows,  18 GPIO  (DS says 19)
  QSOP28    27 rows,  23 GPIO  (DS says 26)
  QFN32     31 rows,  24 GPIO  (DS says 31)
  LQFP48    46 rows,  29 GPIO  (DS says 37)
```

It exits **1**, correctly: the GPIO deficit is the dropped-placeholder rows, and the
LQFP48 gaps at 34 and 45 name exactly which rows lost a dash. A tool that reported this
table as clean would be worse than no tool.

## 4. What is next, in order

1. **Recover the pin numbers from the DS PDF**, which is in the repo:
   `data/sources/l103/datasheets/CH32L103DS0.PDF`, read by
   `tools/recover_l103_pins_from_pdf.py --yaml` by word position, the way X035's lost cells
   were recovered. (This line used to ask a human for a second source; the second source
   was already in the drop, which is exactly why the markdown-first rule now says a
   fallback must prove the markdown cannot answer.) **The recovery is not finished:** it
   runs and checks itself, but four of the five packages still come up short of the DS
   model table's own GPIO count, so its table must not be pasted into a `packages:` block
   until that is explained. Everything else in §1 is read and cited.
2. Then `packages:` from the corrected table, checked against the DS GPIO column per
   package — the check `extract_l103_pins.py` already performs.
3. Then `pins:` (every pin on the die, including the ones no package bonds), `mcu:` from
   §1, and `peripherals:` with `remaps:` from the RM's PCFR1/PCFR2 prose (`:6310`, `:6731`).
4. `gpio:` (three speeds, eight modes — §1), `codegen:` (`RCC_PB2PeriphClockCmd`,
   `style: macro`, `GPIO_PinRemapConfig`), `exti:`/`dma:`/`nvic:` from the RM and the
   `IRQn_Type` enum.
5. `python tools/validate_mcu.py` and `python tools/verify_sdk_names.py` green, then a
   fixture in `tests/fixtures/` and a `data/firmware/platformio.ini` environment — both
   **AGENT-3's area**, so they are a REQUEST rather than an edit.

## 5. Open questions, stated rather than guessed

- **GPIO port width.** Not yet read off `ch32l103_gpio.h`. CH32X035 is 24-bit and
  CH32V006 is 16-bit, so this one is genuinely unknown and must be read, not assumed.
- **`pio_board` / `pio_env` per variant.** Not derivable from the part number and not yet
  looked up in the installed `ch32v` platform. A variant with no board must state nothing,
  and the app then refuses to generate a project for it.
- **ADC channels and internal channels** (Vrefint etc.) — not read yet.
- **Whether the Type-C Rd pull-downs on K8U6/K8U7/F8U6 need a `constraints:` entry.**
  They are a silicon fact about three variants; no DS statement has been read yet about a
  choice the app offers that they would forbid.
