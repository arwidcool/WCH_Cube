## Things worth knowing before you edit this file

**The RM contradicts itself once, and the YAML follows the table.** RM 7.3.2.2, the
AFIO_PCFR1 bit description, spells USART2_RM=101 as `RTS/PA11`. There is no PA11 on this
family — port A stops at PA7. RM Table 7-11 gives `PA1` for the same cell, which is what
this file uses. Anyone re-reading the register prose will hit this; it is a typo in the
source, not a disagreement to resolve.

**TIM2 has complementary outputs and they cost you channels 3 and 4.** RM 12.3.9: "when
complementary outputs are used, channels 3 and 4 act as channel 1 and channel 2
complementary output channels". So CH1N sits on the CH3 pin and CH2N on the CH4 pin, and
there are no extra pins — which is why the `remaps:` block still lists only four signals
and the feature is modelled as a `Complementary Outputs` setting that claims CH3/CH4.
Asking for both plain CH3 output and CH1N is a genuine conflict and the engine flags it.

The Medium-confidence part: the AFIO_PCFR1 prose annotates most remaps as `CH3/CH1N/...`
but omits CH1N for TIM2_RM=001 and 100. That may be real or may be dropped text. The
current model does not encode a per-remap restriction, so it is permissive there.

**Pin 0 is the exposed pad, not a pin.** It is excluded from the I/O count. A pair of
internally shorted GPIOs is one physical pin and counts once. Both rules are enforced.

**Unquoted commas inside `{ }` silently corrupt this file.** YAML flow mappings treat a
comma as a field separator, so

```yaml
- { name: IN8 (Vrefint, internal) }        # WRONG: name becomes "IN8 (Vrefint"
- { name: "IN8 (Vrefint, internal)" }      # right
```

The file still parses, and the app keys per-setting state by choice name, so two choices
whose names both truncate to the same string silently become one. Four live instances of
this were found and fixed on 2026-09-11. `validate_mcu.py` now rejects any unknown key in
a choice, setting, or pin mapping, which is what catches it.

### Three source problems found while doing it

**ADCPRE is not a divider index, and /6 is 16.** RM 3.4.2 lists 21 encodings; the structure
is that bits [4:3] choose a base (00 = /2, 01 = /4, 10 = /6, 11 = /8) and bits [2:0] scale
it (0-3 = x1, 4 = x2, 5 = x4, 6 = x8, 7 = x16), which reproduces every row. Code 8 is
01000 = base /4 x1 = **/4**, so the value proposed on the board for /6 would have run the
ADC 1.5x fast. `codegen.rcc.prescalers.ADC` carries the corrected table.

**ADCPRE has no /1 encoding at all.** Undivided HB clock is ADC_CLK_MODE, bit 31 of the
same register — a separate field. `1` is therefore absent from the values map on purpose:
the generator says "no encoding for 1" rather than silently emitting the /2 code.

**The datasheet contradicts itself on ADC resolution.** DS heading 3.3.14 reads "10-bit ADC
Characteristics", but its own body, DS 1.4.11, DS §1 and RM 9.2 all say 12-bit, and
ADC_RDATAR is DATA[11:0]. It is a stale heading. The data says 12-bit.

### Round 2: the PFIC has two priority bits, not four

Anyone coming from STM32CubeMX will expect four priority bits and a configurable group
split. `PFIC_IPRIORx` (RM 6.5.2.21) gives every vector a byte, but the description says
only bits [7:6] are priority control and "[5:0]: reserved, fixed to 0, write invalid".
Maximum nesting depth is 2 (RM 6.1.1), and the same register description says what the
two bits mean either way: with nesting configured, bit 7 is the preemption level and bit
6 the sub-priority; without it, both are plain priority with nothing preempting. So the
honest UI range is preemption 0-1 and sub 0-1, or a flat 0-3. `nvic.scheme` says exactly
that, and validate_mcu.py checks the ranges against the bit widths so nobody widens them.

**Where nesting is turned on is not in this manual.** PFIC_CFGR (RM 6.5.2.6) is only
KEYCODE and RSTSYS, and no other PFIC register carries a nesting-depth field; on this core
it is a CSR of the QingKe V2 core, documented elsewhere. The two groups are therefore
offered as a labelled choice with no register write claimed for the switch itself.

### Round 2: the vector table has no TIM3 entry, and CH32V006 has a TIM3

RM Table 6-1 runs from vector 2 (NMI) to vector 40 (OPCM) and never mentions TIM3, yet
this part has TIM3 - RM Table 8-2 note (2) describes TIM3's DMA behaviour on CH32V006 and
CH32V007 specifically. Either the table is written for the base family and V006 adds a
vector the manual does not print, or TIM3 here is usable only through DMA and polling. The
table is the only statement available, so **no TIM3 vector is invented** in `nvic:`. If a
WCH EVT header for ch32v00x ever lands in this repo, checking for a `TIM3_IRQn` is the
first thing to do with it.

Confidence on the rest of the table is High: it is a single printed table with vector
numbers, names and entry addresses that agree arithmetically (entry = 4 x number).

### Round 2: PWR, FLASH and EXTI added as real peripherals

The RM chapter list was the checklist (ch.2 PWR, ch.18 FLASH, ch.6.4 EXTI). None of the
three is a stub:

- **PWR** - PVD enable and its four thresholds (PWR_CTLR PLS[6:5], the pairs are rising
  and falling comparator levels, not a tolerance), the regulator mode (LDO_MODE[3:2],
  where code 00 is documented as "unable to configure" and is deliberately not offered),
  sleep versus standby (PDDS), and the auto-wake-up: AWUEN plus a 16-entry prescaler
  whose last two steps are /10240 and /61440 rather than the powers of two the rest of
  the list leads you to expect, plus a 6-bit window where the hardware adds one to the
  value (RM 2.4.4).
- **FLASH** - wait states (FLASH_ACTLR LATENCY[1:0]: 0 to 15 MHz, 1 to 24, 2 to 48; code
  11 reserved) and the user option bytes from Table 18-4: START_MODE, STANDBY_RST,
  IWDG_SW and RDPR. RST_MODE is the fifth option byte and is deliberately NOT here - it
  decides whether a PIN is a reset, so it stays on SYS where the conflict engine sees it.
  Modelling it in two places would let the two disagree.
- **EXTI** - the per-line trigger edge (EXTI_RTENR / EXTI_FTENR, RM 6.4.3), eight lines,
  no signals. The line-to-pin selector stays in the top-level `exti:` block because
  AFIO_EXTICR picks one port per line and that is a pin question.

Still not modelled and deliberately so: ESIG (ch.19) is read-only silicon identity, DBG
(ch.21) is covered by SYS's debug setting, GPIO/AFIO (ch.7) is the pin grid itself, and
PFIC (ch.6) is the `nvic:` block rather than a tree entry.

**Round-3 correction: that list was four and the chapter coverage claim was wrong.**
`tests/completeness.test.js` found **chapter 20, Extended Configuration (EXTEN)**, which
was neither modelled nor declared absent — an undeclared fifth. It is now modelled as a
real peripheral rather than added to the list above, because one of its two bits is not
cosmetic: `TIM2_DMA_REMAP` moves TIM2_CH4's DMA request onto the TIM2 update channel, so
it changes a map this app renders and a conflict it detects. See "EXTEN" below. WRPR0-3 and Data0/Data1 are
option bytes the format cannot express - one bit per pair of sectors, and two free user
bytes - and are listed in FLASH's `notes:` instead of being faked.

### Round 2: the HSE frequency range was wrong, and never had a citation

`clock.sources.HSE.max_mhz` read **25**. Both datasheet tables give **32**: Table 3-9 (from
an external high-speed clock) and Table 3-10 (crystal / ceramic resonator) each list min /
typ / max as 3 / 24 / 32 MHz. The only 25 in either table is note 1 under 3-10 — "25M
crystal ESR is recommended not more than 80 ohm" — which is a recommendation about a
particular crystal, not a ceiling. No row of this notes table ever cited a source for the
25, which is the tell: everything else here names a table.

Nothing is loosened by the correction. `clock.sysclk.max_mhz` is 48 and the PLL is fixed
x2, so HSE above 24 MHz still reddens the tree the moment it feeds the PLL; what changes
is that a 32 MHz crystal driving SYSCLK directly is now accepted, which the part supports.

### Round 2: RCC_CTLR, and why one register was not enough

`codegen.rcc` describes RCC_CFGR0 only, and CFGR0 has no oscillator enables in it —
selecting HSE as the system clock means writing SW there *and* HSEON in RCC_CTLR. The new
`codegen.ctlr` block carries that register: HSION 0, HSIRDY 1, HSEON 16, HSERDY 17, HSEBYP
18, CSSON 19, PLLON 24, PLLRDY 25, all read off RM 3.4.1. Two ordering facts from the same
section are recorded with it: HSEBYP may only be written while HSEON is 0 (RM 3.4.1, bit
18 note), and PLLRDY has to be polled before SW is switched to PLLCLK.

MCO got its encoding at the same time (`codegen.rcc.mco`, RM 3.4.2 bits [26:24]): 0xx is
"no output", 100 SYSCLK, 101 HSI, 110 HSE, 111 PLLCLK. It is a sparse field, so Disable is
0 rather than the next index down.

### Round 2: a stale inherited reference on CH32V005

CH32V005 removes TKEY and TIM3, but inherited `codegen.analog_signals.TKEY` and
`codegen.periph_clock.PB1.bits.TIM3` from this file — the generator would have marked
TouchKey pins analog and emitted a TIM3 clock enable on a part with neither. Both are now
in that file's `mcu.remove` list. Found by the new `codegen` name check in
`validate_mcu.py`, not by reading: `inherits:` makes every addition here an addition to
every child, so a new `codegen` entry naming a peripheral is worth a thought about V005.

### And one correction to this file's own earlier claim

The clock note used to say "Single HB domain — no APB1/APB2 split". There is indeed only
one prescaler (HPRE), so every peripheral runs at HCLK — but PB1 and PB2 do exist as clock
ENABLE domains (RCC_PB2PCENR at 0x40021018, RCC_PB1PCENR at 0x4002101C). Membership is in
`codegen.periph_clock`. TKEY and OPA have no enable bit stated in RM 3.4.6-3.4.8 and are
deliberately absent rather than guessed at.

### Sampling time depends on a mode bit

ADC SMPx[2:0] means different cycle counts depending on ADC_LP (RM 9.3.4). The `sample`
parameter lists the normal-mode figures and says so; codes 010/011/100 mean 13.5/28.5/41.5
cycles in low-power mode instead of 11.5/19.5/35.5. Total conversion is sampling + 12.5
ADC clocks, not + 11.

## Round 3 — what the EVT package settled, and what a compiler found

The WCH EVT package for this part landed in `data/sources/V006/Evt/`. Its SPL headers are
in `data/sources/V006/Evt/EXAM/SRC/Peripheral/inc/`, and by the precedence rule in
`data/sources/README.md` they now outrank the reference manual for anything with a *name*.
Everything below is cited from those files, not from the PlatformIO copy.

### Confirmed — the port-clock spelling (HUMAN_TODO item 5, closed)

Recorded above as an assumption; it is now checked:

| Name | Where | Line |
|---|---|---|
| `RCC_PB2PeriphClockCmd(uint32_t, FunctionalState)` | `Evt/EXAM/SRC/Peripheral/inc/ch32v00X_rcc.h` | 157 |
| `RCC_PB2Periph_AFIO` | same | 88 |
| `RCC_PB2Periph_GPIOA` … `RCC_PB2Periph_GPIOD` | same | 89–92 |
| `AFIO_TypeDef.PCFR1` | `Evt/EXAM/SRC/Peripheral/inc/ch32v00X.h` | 197 |

The `RCC_APB2PeriphClockCmd` spelling is real, but it belongs to CH32X035, not here. The
two families are not interchangeable and neither may be inherited from the other by
analogy.

### Corrected — `codegen.header` named the CH32V003 header

It read `ch32v00x.h`. This part's header is **`ch32v00X.h`, capital X**:
`Evt/EXAM/SRC/Peripheral/inc/ch32v00X.h` line 2 gives `File Name : ch32v00X.h` and line 12
the guard `__CH32V00X_H`.

This was not a typo with a cosmetic cost. The SDK ships **both** series side by side —
`~/.platformio/packages/framework-wch-noneos-sdk/Peripheral/` contains `ch32v00Xx` (this
part) *and* `ch32v00x` (CH32V003), with different register maps. NTFS resolved the wrong
case to the right file, so every test and every browser pass was blind to it; a
case-sensitive filesystem fails the build, and a machine with both include paths compiles
the other part's registers without a word.

### Corrected — this part has ONE GPIO output speed, and the UI was offering three

`codegen.speeds` read `GPIO_Speed_2MHz / 10MHz / 50MHz`. Those are the CH32V10x/20x/30x
spellings; none of them exists here. `GPIOSpeed_TypeDef` in
`Evt/EXAM/SRC/Peripheral/inc/ch32v00X_gpio.h` lines 23–26 is:

```c
/* Output Maximum frequency selection */
typedef enum
{
    GPIO_Speed_30MHz = 1,
} GPIOSpeed_TypeDef;
```

One member. The RM agrees and explains why: `GPIOx_CFGLR.MODEy` is a **single bit**
(RM v1.4 §7.3.1.1 — *"1: Output mode, maximum speed 30MHz; 0: Input mode"*), so there is
no encoding for a second speed to occupy. EVT and the RM do not contradict each other
here; they agree from two directions.

So the defect was larger than a misspelling: **the GPIO table was offering the user a
Low/Medium/High choice the silicon does not have.** The fix is in the data, not in the UI,
so that no part name is ever hardcoded in a renderer: the new top-level `gpio.speeds` list
states what this part offers, and `data/FORMAT.md` defines a one-entry list as *the
control is not shown* — not *shown disabled*. `codegen.speeds` keeps `Low`/`Medium`/`High`
as aliases onto the one real macro purely so a `.wchproj` saved before this fix still
generates code that compiles; they are not an offer, and the UI must read `gpio.speeds`.

### Why none of this was caught before

267 tests, a validator with fourteen planted breaks, and a real browser all passed. None of
them could see it: every name involved is a plausible, correctly-spelled SPL identifier
that belongs to a different chip. Only a compiler disagrees. Hence the round's rule and
`tools/verify_sdk_names.py`.

## The two Medium-confidence rows, settled by EVT

Both were recorded in the confidence table above as "confirm against the RM/an EVT header".
The package landed; here is what it said.

### TouchKey channel → pin: CONFIRMED, and the mechanism explains why

The table listed *"TouchKey channels = ADC input pins (inferred mapping CHx = INx)"* at
Medium confidence, from DS 1.4.11.

It is right, and the reason is stronger than a mapping: **TouchKey is not a separate
peripheral at all — it is a mode of the ADC.** There is no `ch32v00X_tkey.h` in the EVT
`Peripheral/inc/` listing, and `ch32v00X.h:475` defines

```c
#define TKey1    ((ADC_TypeDef *)ADC1_BASE)
```

— the same base address as ADC1. The driver API lives in `ch32v00X_adc.h`:
`ADC_TKeyCmd` (188), `ADC_BufferCmd` (187), `ADC_Tkey_CurrentConfig` (189),
`ADC_TKey_MulShieldCmd` (193). Channels are the ordinary `ADC_Channel_0..9` macros
(adc.h:67–76), selected through the ordinary `ADC_RegularChannelConfig`.

`EXAM/TOUCHKEY/.../main.c` then pins it down concretely. Its header comment reads *"This
example demonstrates channel 2 (PC4)"*, and the code configures `GPIO_Pin_4` on `GPIOC` as
`GPIO_Mode_AIN` before enabling TouchKey. This file has `TKEY.CH2 = PC4` and
`ADC1.IN2 = PC4`. They agree, and they agree for the right reason.

**Row promoted from Medium to High.** Two consequences worth carrying forward:

- A TouchKey channel and the ADC channel of the same number are **the same pin and the
  same hardware**, so claiming both is claiming one pin twice. The conflict engine already
  sees this because the two peripherals route to the same pins.
- Generated code for TouchKey is ADC code plus `ADC_TKeyCmd(ADC1, ENABLE)`. There is no
  TKey init struct to fill in and none should be invented.

### The OPA polling set: our shape was WRONG, and one option was impossible

`ch32v00X_opa.h` is explicit, and it corrects this file rather than confirming it.

```c
typedef enum { CHP_POLL_NUM_1 = 0, CHP_POLL_NUM_2, CHP_POLL_NUM_3 } OPA_PSEL_POLL_NUM_TypeDef;
typedef enum { OPA_POLL_CH1_PA2 = 0, OPA_POLL_CH1_PD7, OPA_POLL_CH1_PD3, OPA_POLL_CH1_PD1 } OPA_POLL_CH1_TypeDef;
```

and `OPA_InitTypeDef` carries `POLL_NUM`, `POLL_CH1`, `POLL_CH2`, `POLL_CH3`, `POLL_SEL`.

Two facts follow, and this file had both wrong:

1. **Three polled channels is the maximum.** The old `Polling P0/P1/P2/P3` choice asked
   for four. It is removed — it offered the user a configuration the silicon cannot
   express, which is precisely what round 3 exists to stop.
2. **The polled set is not fixed.** Each of the three slots independently selects any of
   PA2 / PD7 / PD3 / PD1 — that is, any of P0..P3. The old single `Polling P0/P1/P2`
   choice hardcoded one arbitrary set out of ten legal ones. All ten (the six pairs and
   the four triples) are now offered.

The P0..P3 pin assignments themselves are **confirmed**: `OPA_POLL_CH1_PA2/PD7/PD3/PD1`
matches this file's `P0: PA2, P1: PD7, P2: PD3, P3: PD1` exactly.

`POLL_NUM` and `POLL_CH1..3` are deliberately **not** offered as parameters. They are
derived by the generator from the chosen set, because a user-settable `POLL_NUM` could
contradict the set and then the claimed pins and the written register would disagree —
the "one fact in two places" rule in `data/FORMAT.md`.

`OPA1` also gained the non-pin parameters the header settles: `POLL_SEL` (software, or
TIM1_CH4 / TIM2_CH4 / TIM3_CH1 / TIM3_CH2), `POLL_AT`, `SETUP_CFG`, `OPA_HS`, `OUT_IE`,
`NMI_IE`. Note `OPA_SETUP_CFG_2 = 3`, not 2 — the enum skips a value, so the option index
is not the register value there.

**And a consequence for CH32V005, caught by the rule this round wrote down.** That part has
no polling *and* no TIM3, so inheriting `poll_trigger` would have offered it three trigger
options naming a timer it does not have. Its `OPA1` now restates `params:` without the two
polling entries — a list replaces wholesale, the same mechanism its `settings:` already
used. This is the "a new entry in the parent is a new entry in every child" hazard in
`data/FORMAT.md`, hitting for real within an hour of being documented.

## Round 3: EXTEN (RM ch.20), and a DMA request that moves

Found by `tests/completeness.test.js` as an RM chapter that was neither modelled nor on
the declared-absence list. Modelled, because it is not cosmetic.

The RM and the EVT header agree exactly on all three bits — worth recording, because on
the TIM3 vector they did not:

| Bit | Name | Value | EVT | RM |
|---|---|---|---|---|
| 6 | `EXTEN_LOCKUP_EN` | `0x00000040` | `ch32v00X.h`:2516 | 20.2.1 |
| 7 | `EXTEN_LOCKUP_RSTF` | `0x00000080` | `ch32v00X.h`:2517 | 20.2.1 |
| 16 | `EXTEN_TIM2_DMA_REMAP` | `0x00010000` | `ch32v00X.h`:2519 | 20.2.1 |

The register block is `EXTEN` with a single member `EXTEN_CTR` (`ch32v00X.h`:385, 470),
at 0x40023800, reset 0x00000400.

**There is no SPL driver.** EVT ships no `ch32v00X_exten.h` and `ch32v00X.h` declares no
function for the unit, so generated code writes the register directly — the same shape as
ADC's low-power bit, and recorded the same way with `sdk_none: true` plus a note.

### LKUPRST is deliberately not offered

It is a write-1-to-clear *status* flag reporting that a lock-up already reset the part.
That is something firmware reads at startup, not something a configurator sets. Offering
it would be offering a control that does nothing useful at init time — a dead control by
round 2's rule, just one that happens to be writable.

### The part that is not cosmetic: `dma.remaps`

RM 20.1 item 2: *"The updated DMA channel can be shared between the DMA request of TIM2
channel 4 and the updated DMA request."* So with `TIM2_DMA_REMAP` set, TIM2_CH4 is served
by the channel that carries TIM2_UP — channel 2 — and its own entry on channel 7 no
longer applies.

**The channel a user sees for a request therefore depends on a setting of a different
peripheral.** That is the same coupling shape as `clock.hse_peripheral` / `hse_setting`,
which round 2 added so that picking HSE could enable the crystal, and it is stated in the
data for the same reason: so no renderer has to know it.

New `dma.remaps` key, one entry, carrying the peripheral and setting that trigger it, the
register and macro to write, and `moves: { request, from_channel, to_channel }`.
`dma.requests` in this file remains the remap-OFF map, which is the reset state —
`EXTEN_CTR` resets to 0x00000400 with bit 16 clear.

CH32V005 inherits all of it unchanged: it has TIM2, and its `dma.requests` puts TIM2_UP on
channel 2 and TIM2_CH4 on channel 7 exactly as the parent does.

## Round 5: audit for the constraint class - ONE instance exists here, and it is NOT filled

Round 5's rule is that a choice the app offers must be one the silicon can honour, and the
mechanism for saying so is the `constraints:` block documented in `data/FORMAT.md`. This
part was audited against all three shapes that mechanism was built for. The result is a
finding, recorded here with its citations so that "no instances" is not the silent answer.

### Shape 2 - a shorted pair may not be an output: **YES, on this part**

`data/sources/V006/Datasheets/CH32V006DS0.md` p.19:

- **Note 3** - *"For CH32V006E8R and CH32V005E6R6 chips, the PA1 and PA6 pins are
  short-connected and sealed inside the chip, which forbids the two I/O to be configured
  as the output function."*
- **Note 4** - *"For CH32V006F8U7, CH32V006F8P7, CH32V006D8U7, CH32V005F6U6,
  CH32V005F6P6 and CH32V005D6U6 chips, the PA4 and PD7 pins are short-jointed and sealed
  inside the chip, and it is forbidden that both of the two IMAGO are configured as output
  functions."*

("IMAGO" is a bad translation in the source, not a third pin.) The pins it names are
exactly the pairs the `packages:` tables already mark shorted - `[PA1, PA6]` on QSOP24
pin 17, `[PD7, PA4]` on QFN20 pin 1, TSSOP20 pin 4 and QFN12 pin 12 - which is a
cross-check on both readings. The shape that carries it is one entry per note:

```yaml
  - id: shorted-pa1-pa6-not-output
    option: gpio.mode
    classes: [out]
    not_on: [PA1, PA6]
    packages: [QSOP24]
    reason: "..."
    source: "CH32V006DS0.md Note 3 (p.19)"
```

**It is deliberately NOT in the file this round.** Deliverable A's acceptance test
requires CH32V006 and CH32V005 to be **byte-identical in behaviour** before and after the
mechanism lands, precisely so that a mechanism which only works for the part it was
designed against is caught. Filling this would change this part's GPIO table by design,
which is a different act from the regression the test is guarding - and doing both at once
would leave no way to tell which one a diff came from. It is a **one-entry-per-note
addition needing no code change** (the `classes:` field is the only thing this file would
need alongside it), and it should land as its own clearly labelled change with the
regression baseline already recorded.

**Open line, on the board:** when it lands, `app/tests/codegen.test.js` assigns
`GPIO_Output` to `PA4` and `app/tests/api.test.js` does the same, both through the TSSOP20
`PD7/PA4` pair, and both expect a GPIO plan. Those are the tests this change would have to
answer, and they are APP's and QA's, not DATA's - which is the second reason not to fold it
in unannounced.

### Shape 1 - a pull that exists on some pins and not others: **NO**

`CH32V006DS0.md` ch.1.4.16: *"All GPIO pins support controllable pull-up and pull-down
resistors."* There is no per-pin carve-out, so `GPIO_Mode_IPD` needs no constraint here.
The EVT header agrees by omission: `ch32v00X_gpio.h:33` declares `GPIO_Mode_IPD = 0x28`
with no restricting comment, where `ch32x035_gpio.h:33` carries one.

One sentence in the same chapter is worth recording without acting on it: *"When PD7, PA7
and PC5 are used as reset pins, the pull-up resistor is turned on and the pull-down
resistor is turned off by default."* That is the reset pin's power-on state, not a choice
the GPIO table offers, so it is not a constraint - it is a fact about `SYS`.

### Shape 3 - illegal while another peripheral is on: **NO USB, but a fourth shape exists**

This part has no USB peripheral at all, so the CH32X035 case has no counterpart.

The audit did find a conditional restriction, and it is one the current mechanism **cannot
express**: `CH32V006DS0.md` ch.1.4.16 says *"When PA1 and PA2 are crystal pins, i.e.,
PA1PA2_RM = 1, PA1 and PA2 cannot be used for GPIO functions."* That is conditional on a
**remap/clock state** - an AFIO field, `PA1PA2_RM` - not on a peripheral being enabled, so
`when: { peripheral: ..., enabled: ... }` does not reach it. Recorded rather than stretched
to fit: `when:` is a peripheral-state predicate, and widening it to "any model key" without
a second real instance would make the schema general in a way nothing tests.

**Net result: this part has one instance of the class, shape 2, unfilled on purpose; shapes
1 and 3 are absent, with the source read and quoted above rather than assumed.**
