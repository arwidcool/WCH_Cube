## Things worth knowing before you edit this file

**The RM contradicts itself once, and the YAML follows the table.** RM 7.3.2.2, the
AFIO_PCFR1 bit description, spells USART2_RM=101 as `RTS/PA11`. There is no PA11 on this
family — port A stops at PA7. RM Table 7-11 gives `PA1` for the same cell, which is what
this file uses. Anyone re-reading the register prose will hit this; it is a typo in the
source, not a disagreement to resolve.

**TIM2 has complementary outputs and they cost you channels 3 and 4.** RM 12.3.9: "when
complementary outputs are used, channels 3 and 4 act as channel 1 and channel 2
complementary output channels". So CH1N sits on the CH3 pin and CH2N on the CH4 pin, and
there are no extra pins — which is why the `remaps:` block still lists only four signals
and the feature is modelled as a `Complementary Outputs` setting that claims CH3/CH4.
Asking for both plain CH3 output and CH1N is a genuine conflict and the engine flags it.

The Medium-confidence part: the AFIO_PCFR1 prose annotates most remaps as `CH3/CH1N/...`
but omits CH1N for TIM2_RM=001 and 100. That may be real or may be dropped text. The
current model does not encode a per-remap restriction, so it is permissive there.

**Pin 0 is the exposed pad, not a pin.** It is excluded from the I/O count. A pair of
internally shorted GPIOs is one physical pin and counts once. Both rules are enforced.

**Unquoted commas inside `{ }` silently corrupt this file.** YAML flow mappings treat a
comma as a field separator, so

```yaml
- { name: IN8 (Vrefint, internal) }        # WRONG: name becomes "IN8 (Vrefint"
- { name: "IN8 (Vrefint, internal)" }      # right
```

The file still parses, and the app keys per-setting state by choice name, so two choices
whose names both truncate to the same string silently become one. Four live instances of
this were found and fixed on 2026-09-11. `validate_mcu.py` now rejects any unknown key in
a choice, setting, or pin mapping, which is what catches it.

### Three source problems found while doing it

**ADCPRE is not a divider index, and /6 is 16.** RM 3.4.2 lists 21 encodings; the structure
is that bits [4:3] choose a base (00 = /2, 01 = /4, 10 = /6, 11 = /8) and bits [2:0] scale
it (0-3 = x1, 4 = x2, 5 = x4, 6 = x8, 7 = x16), which reproduces every row. Code 8 is
01000 = base /4 x1 = **/4**, so the value proposed on the board for /6 would have run the
ADC 1.5x fast. `codegen.rcc.prescalers.ADC` carries the corrected table.

**ADCPRE has no /1 encoding at all.** Undivided HB clock is ADC_CLK_MODE, bit 31 of the
same register — a separate field. `1` is therefore absent from the values map on purpose:
the generator says "no encoding for 1" rather than silently emitting the /2 code.

**The datasheet contradicts itself on ADC resolution.** DS heading 3.3.14 reads "10-bit ADC
Characteristics", but its own body, DS 1.4.11, DS §1 and RM 9.2 all say 12-bit, and
ADC_RDATAR is DATA[11:0]. It is a stale heading. The data says 12-bit.

### And one correction to this file's own earlier claim

The clock note used to say "Single HB domain — no APB1/APB2 split". There is indeed only
one prescaler (HPRE), so every peripheral runs at HCLK — but PB1 and PB2 do exist as clock
ENABLE domains (RCC_PB2PCENR at 0x40021018, RCC_PB1PCENR at 0x4002101C). Membership is in
`codegen.periph_clock`. TKEY and OPA have no enable bit stated in RM 3.4.6-3.4.8 and are
deliberately absent rather than guessed at.

### Sampling time depends on a mode bit

ADC SMPx[2:0] means different cycle counts depending on ADC_LP (RM 9.3.4). The `sample`
parameter lists the normal-mode figures and says so; codes 010/011/100 mean 13.5/28.5/41.5
cycles in low-power mode instead of 11.5/19.5/35.5. Total conversion is sampling + 12.5
ADC clocks, not + 11.
