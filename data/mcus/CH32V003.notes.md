## Why this is NOT `inherits: CH32V006`

It is the obvious idea and it is wrong, for the same reason CH32X035 is not a delta of
CH32V006: **they are different SPL series.** CH32V003 is series `ch32v00x`, header
`ch32v00x.h`; CH32V005/CH32V006 are series `ch32v00Xx`, header `ch32v00X.h` — capital X.
Both are installed side by side in `framework-wch-noneos-sdk/Peripheral/`, and on NTFS the
wrong one resolves silently. `genericCH32V003F4P6.json` states it outright:
`"spl_series": "ch32v00x"`.

The differences are not cosmetic. Every row below is a name or a number that is correct on
one part and wrong on the other:

| | CH32V003 | CH32V005 / CH32V006 |
|---|---|---|
| SPL series / header | `ch32v00x` / `ch32v00x.h` | `ch32v00Xx` / `ch32v00X.h` |
| Core | RV32EC | RV32E**m**C |
| Ports | A (PA1–PA2 only), C, D | A, B, C, D |
| GPIO output speeds | **three** — `GPIO_Speed_10MHz`, `_2MHz`, `_30MHz` | **one** — `GPIO_Speed_30MHz` |
| Port clock macros | `RCC_APB2PeriphClockCmd` / `RCC_APB2Periph_GPIOA` | `RCC_PB2PeriphClockCmd` / `RCC_PB2Periph_GPIOA` |
| ADC resolution | 10-bit | 12-bit |
| ADC sample-time macros | `ADC_SampleTime_3Cycles` … `_241Cycles` | `ADC_SampleTime_CyclesMode0` … `7` |
| ADC clock ceiling | 24 MHz | 48 MHz |
| Flash wait states | 2 codes (0, 1) | 3 codes (0, 1, 2) |
| PVD thresholds | 8, 2.85–4.4 V | 4, 1.87–2.66 V |
| HSE range | 4–25 MHz | 3–32 MHz |
| TIM1_RM field width | 2 bits, 4 mappings | 4 bits, 10 mappings |
| USART1_RM / I2C1_RM | **split** across bits 2+21 and 1+22 | contiguous, `[9:6]` and `[5:3]` |
| TIM2 complementary outputs | none | CH1N/CH2N on the CH3/CH4 pins |
| OPA init struct | 2 members (PSEL, NSEL) | 13 members incl. a polling engine |
| TIM3, USART2, TouchKey | absent | present (TIM3/TKEY not on V005) |
| Vector 3 `irqn` | `EXC_IRQn` | `HardFault_IRQn` |
| Highest vector | 38 (TIM2) | 40 (OPCM) |

A `remove:` list long enough to express that would be longer than the file, and every
`maps merge, the child wins` rule would still leave the child inheriting `codegen.speeds`
keys and `periph_clock` macro prefixes that do not compile. Written standalone.

## Source problems found while doing this

### 1. RM 7.3.2.1 bit 17 contradicts its own Table 7-13 and the pin table

`ADC_ETRGINJ_RM` is bit 17 of AFIO_PCFR1. Its description in RM 7.3.2.1 reads, verbatim:

> **17 ADC_ETRGINJ_RM** RW — Remap bit for ADC external trigger **rule** conversion.
> 0: ADC external trigger rule conversion connected to PD3.
> 1: ADC external trigger rule conversion connected to PC2.

That is a copy of bit 18's text, word for word — "rule" (regular) instead of "injected",
and PD3/PC2 instead of the injected pins. RM Table 7-13 (the injected-trigger table) says
PD1 and PA2, and DS Table 2-2 agrees independently: PD1 carries `AETR2` and PA2 carries
`AETR2_1`, where the trailing `_1` is the datasheet's own notation for "AFIO bit = 1".

**The YAML follows the table and the pin map: IETR0 = PD1, IETR1 = PA2.** Two sources
against one that is visibly a duplicated paragraph.

### 2. The RM calls GPIO speed code 11 "50 MHz" and the SDK calls it "30 MHz"

RM 7.3.1.1, `GPIOx_CFGLR.MODEy[1:0]`:

> 00: Input mode. 01: Output mode, maximum speed 10MHz. 10: Output mode, maximum speed
> 2MHz. **11: Output mode, maximum speed 50MHz.**

The EVT header, `ch32v00x_gpio.h:22-29`, gives the same three codes as
`GPIO_Speed_10MHz = 1`, `GPIO_Speed_2MHz`, `GPIO_Speed_30MHz`, and then adds
`#define GPIO_Speed_50MHz GPIO_Speed_30MHz`.

They are the same two bits either way, so nothing is at stake in the generated code. The
YAML uses the SDK's names — EVT outranks the RM for anything the software has to *name* —
and records the disagreement in a `pins_note:` on that entry. `GPIO_Speed_50MHz` is an
**alias, not a fourth speed**, and is deliberately absent from `gpio.speeds`: two rows
that write identical bits would be a choice the user cannot actually make. It is present
in `codegen.speeds` as a translation key, so a `.wchproj` carrying that name still
generates code that compiles.

### 3. `FLASH_OBR` and the user option byte spell the same two bits differently

RM 16.3.7 calls them `STANDY_RST` and `IWDG_SW`; RM 16.4's user-option-byte table calls
them `STANDYRST` and `IWDGSW`. (Both misspell "standby", consistently.) The YAML uses the
option-byte table's spelling in the `FLASH` settings, because that block is about
programming the option byte, not about reading `FLASH_OBR`.

### 4. DS Table 2-2 abbreviates, and one abbreviation is ambiguous

The pin-arrangement drawings use `T1CH1CH2N_` and `T1CH1CH3N_` as single tokens — they
are two functions run together (`T1CH1_1` and `T1CH2N_1` on PC4, `T1CH1_1` and `T1CH3N_3`
on PC6), not one function with a strange name. Table 2-1's remapping column separates
them properly and is what the YAML follows.

## Things worth knowing before you edit this file

### Port A has two pins, and one of them is not PA0

`GPIOA` on this part is **PA1 and PA2 and nothing else** (RM Figure 1-1: "GPIOA PA1 ~
PA2"). Anything that iterates `PA0..PA7` invents six pins. This bites in one visible
place: `exti.lines.EXTI0` has **no `"00"` entry**, because AFIO_EXTICR selecting port A
for line 0 would select a pin that does not exist. Lines 1 and 2 are the only ones that
can reach port A at all.

There is also **no port B**. AFIO_EXTICR value `01` is simply not listed in RM 7.3.2.2,
and `ch32v00x_rcc.h` defines `RCC_APB2Periph_GPIOA`, `_GPIOC` and `_GPIOD` with nothing
between them.

### The SOP8 part bonds five GPIOs onto two pads

`CH32V003J4M6` is the reason the `packages:` list-value syntax exists on this part:

```
1: [PD6, PA1]
8: [PD4, PD5, PD1]
```

DS Table 2-1 gives PD6 and PA1 the same SOP8 pin number, and PD4, PD5 and PD1 the same
one. Eleven GPIOs reach eight pads, six of which are I/O — which is exactly the DS model
table's `6`, and `validate_mcu.py` asserts it.

**PD7 has no pad on SOP8.** So that package has no external reset pin, and no `PD0`,
`PC0`, `PC3`, `PC5`, `PC6` or `PC7` either. The `SYS` peripheral still maps `RST` to PD7
— the option byte defaults to holding it on every die — so on SOP8 the engine reports
*"RST needs PD7, which is not bonded on SOP8"*. That message is correct and should not be
"fixed": the configuration really is unreachable there.

### `remap` index is the register value, and two of the fields are split

`codegen.remap.fields` reassembles the two split fields:

```yaml
I2C1:   [{ lsb: 1, bits: 1 }, { lsb: 22, bits: 1, from: 1 }]
USART1: [{ lsb: 2, bits: 1 }, { lsb: 21, bits: 1, from: 1 }]
```

The manual writes these as `[22,1]` and `[21,2]`, high bit first — the low bit sits in the
low half of AFIO_PCFR1 and the high bit eleven bits away in the high half. The remap index
in `peripherals:` is the assembled two-bit value.

I2C1 entries **2 and 3 are identical on purpose**. The manual writes the third mapping as
`1X`, meaning both `10` and `11` select SCL/PC5 + SDA/PC6. Index *is* register value, so
skipping index 3 would make the generator write `2` where the user chose `3`.

### The ADC prescaler codes are the EVT's, not CH32V006's

Bits [4:3] of `ADCPRE` pick a base (`00` /2, `01` /4, `10` /6, `11` /8) and bits [2:0]
scale it (`0-3` ×1, `4` ×2, `5` ×4, `6` ×8, `7` ×16), so several dividers have two legal
codes. The values in `codegen.rcc.prescalers.ADC` were derived mechanically from
`ch32v00x_rcc.h:68-79` by shifting each `RCC_PCLK2_DivN` macro right by 11:

```
Div2 0   Div4 8   Div6 16  Div8 24  Div12 20  Div16 28
Div24 21 Div32 29 Div48 22 Div64 30 Div96 23  Div128 31
```

Two of them differ from the code CH32V006's file picks for the same divider (/4 is 8 here
and 4 there; /8 is 24 here and 12 there). Both are legal and produce the same divider —
this is *not* a defect in either file — but matching WCH's own SDK is one fewer thing to
explain to someone diffing generated code against an EVT example.

**There is no /1 at all**, and unlike CH32V006 there is not even a separate bit for it:
RM 3.4.2 marks CFGR0 [31:27] reserved, so this part has no `ADC_CLK_MODE`.

### Vector 3 is the strongest case yet for two names per vector

`data/FORMAT.md` says `irqn` and `handler` are not interchangeable and must each be taken
from their own source. On CH32V006 the worked example is `ADC_IRQn` / `ADC1_IRQHandler`,
where at least the words overlap. Here:

| Vector | `irqn` (ch32v00x.h) | `handler` (startup_ch32v00x.S) |
|---|---|---|
| 3 | `EXC_IRQn` | `HardFault_Handler` |
| 2 | `NonMaskableInt_IRQn` | `NMI_Handler` |
| 29 | `ADC_IRQn` | `ADC1_IRQHandler` |

`EXC_IRQn` and `HardFault_Handler` share no substring. Deriving either from the other is
not a heuristic that can be made to work.

## Round 5: audit for the constraint class — **no instance exists on this part**

`data/FORMAT.md`'s `constraints:` mechanism was checked against this part's sources, shape
by shape. **All three come back negative, so `CH32V003.yaml` has no `constraints:`
block** — which, per FORMAT.md, leaves its behaviour identical to a part from before the
mechanism existed. The audit is written down because an absent block looks exactly like a
forgotten one.

### Shape 1 — a choice that exists on some pins and not others: **NO**

CH32X035's instance is a comment on the enum member itself:
*"Only PA0--PA15 and PC16--PC17 support input pull-down"* (`ch32x035_gpio.h:33`).
`ch32v00x_gpio.h:32-42` carries **no note of any kind** on any `GPIOMode_TypeDef` member,
and RM 7.3.1.1's `GPIOx_CFGLR` description states `CNFy = 10` ("with pull-up and pull-down
mode") for every pin of every port without qualification. Nothing per-pin to state.

### Shape 2 — a shorted group may not be driven as an output: **NOT STATED, so NOT WRITTEN**

This is the one that looked most likely, and it is the one worth being careful about.

The physical situation is the same as CH32X035's: SOP8 bonds `PD6+PA1` on pad 1 and
`PD4+PD5+PD1` on pad 8, so two — or three — independent output drivers can fight over one
pad. On CH32X035 the datasheet says so, and the rule is
`shorted-pc10-pc11-pc16-pc17-not-output`, citing *DS Note 4*.

**The CH32V003 datasheet says nothing of the kind.** There is no note under Table 2-1, no
note against the `CH32V003J4M6` pin drawing, and no sentence anywhere in the DS or the RM
about configuring bonded pins. Grepping the DS for `short`, `bond`, `internally connected`
and `prohibit` returns nothing relevant.

So the rule is **not** written here. "The other CH32 parts have it" is precisely the
citation-free assumption that produced `GPIO_Speed_50MHz` in round 3 and
`GPIO_Mode_Out_OD` in round 4, and writing a constraint the silicon may not have would
remove a choice the user is entitled to make — the mirror image of the defect the
mechanism exists to prevent, and just as invisible.

Recorded here as an **open question**, not as a rule. What would settle it: a note in a
later DS revision, or a statement in WCH's `CH32V003J4M6` application material. Until
then, the honest position is that the app offers the configuration and the engineer is
responsible for not driving two bonded drivers against each other — which is also what
the conflict engine already shows, because both names resolve to one canonical pin and a
second claim on it is flagged.

### Shape 3 — illegal while another peripheral is on: **NO candidate**

CH32X035's instance is *"PC10 and PC11 must be floating inputs while USB is enabled"*.
This part has **no USB**, no USBPD and nothing else that couples a peripheral's enable
state to a pin's legality. The two pin-affecting AFIO bits that come close — `PA12_RM`
(PA1/PA2 become the crystal pins) and `RST_MODE` (PD7 becomes the reset) — are both
already modelled the right way: as `settings:` whose choices claim signals, so the
ordinary conflict engine sees them. A constraint would be a second mechanism saying the
same thing, and two mechanisms that can disagree is how the GPIO speed defect shipped
twice.

## Not modelled, deliberately — with the citation for each

Listed so that "we meant to" and "the silicon does not have it" stay distinguishable.

| What | Why | Source |
|---|---|---|
| `USART1_CK` (the synchronous clock pin) | The pin is real and the SPL can drive it, but driving it needs a **second** init struct, `USART_ClockInitTypeDef` + `USART_ClockInit`, and the generator has no way to gate a second struct off when the mode does not use it. Claiming the pad without configuring it would be worse than not offering it. CH32V006 omits it for the same reason. **Open**, not absent. | RM Table 7-10; `ch32v00x_usart.h:51-66,156` |
| ADC low-power bit | Absent from the silicon, not just from the model: CH32V006 has `ADC_CTLR3.ADC_LP`; **CH32V003 has no `ADC_CTLR3`** in its ADC register list. Nothing to write. | RM 9.3 register list |
| `TIM2` repetition counter | `TIMx_RPTCR` is an advanced-timer register. TIM2 is the general-purpose timer here and has none. | RM ch.11 |
| TIM2 complementary outputs | CH32V006's TIM2 drives CH1N/CH2N onto the CH3/CH4 pins. This one cannot: RM ch.11 describes no complementary channel and `ch32v00x_tim.h` marks all four complementary `TIM_OCInitTypeDef` members *"valid only for TIM1"*. | `ch32v00x_tim.h:57,67,71,75` |
| `EXTEN_TIM2_DMA_REMAP` | The bit does not exist. CH32V006 has it at `EXTEND_CTR` bit 16; **bit 16 here is `OPA_EN`.** So `dma:` has no `remaps:` block. | RM 17.2.1; `ch32v00x.h:2195` |
| OPA interrupt vector | There is none. `IRQn_Type` ends at `TIM2_IRQn = 38` and the startup table ends at `TIM2_IRQHandler`; CH32V006 has `OPCM_IRQn = 40`. A vector that is absent is absent — none was added for symmetry. **See the action item below.** | `ch32v00x.h`; `startup_ch32v00x.S` |
| OPA `params:` | The whole of `OPA_InitTypeDef` is `PSEL` and `NSEL`, and **both decide which pin the amplifier looks at** — so both are `settings:` where the conflict engine can see them, and nothing is left over to be a parameter. This is a complete model, not a gap; `tests/completeness.test.js` counts it as a missing cell because it counts cells, not completeness. | `ch32v00x_opa.h:38-42` |
| `FLASH` WRPR / Data0 / Data1 option bytes | Per-project values rather than configuration choices, and the format has nothing to express "one bit per pair of sectors". Same treatment as CH32V006. | RM 16.4 |
| Interrupt vs. event on EXTI lines | `EXTI_INTENR` vs `EXTI_EVENR` — an event wakes the core from WFE without running a handler, which is a code decision rather than a pinout one. Same treatment as CH32V006. | RM 6.4 |

1. **`tests/completeness.test.js` needs one line.** The suite is red on exactly one cell:

   That is a true statement about the silicon, and the file's `ABSENT` map is where such a

   ```js
     + 'ch32v00x.h ends at TIM2_IRQn = 38 and startup_ch32v00x.S agrees. CH32V006 has '
     + 'OPCM_IRQn = 40; CH32V003 does not',
   ```

   **Not applied here**, because `tests/` was being edited by another agent during this
   change and the instruction for this pass was to add files rather than edit them. It is
   one line and it is the only thing standing between this part and a green suite.

2. **`dist/index.html` has not been rebuilt.** `tests/build.test.js` is red for the
   ordinary reason — a new data file is not inlined until `python build.py` runs. The
   rebuild was skipped on purpose: `app/` and `build.py` were both dirty in the working
   tree while this was written, so a rebuild would have baked someone else's in-flight
   work into a committed artifact. Run `python build.py && node tests/run.js` once the
   tree is quiet.

3. **Point `tools/extract_remaps.py` at this manual.** The tool is written against the
   CH32V00X RM's table layout. Three agreeing sources is good; a machine diff is the
   standard this repo set for CH32V006 (232 assignments, 0 differences) and this part has
   not met it.

4. **`data/sources/V003/` is lower-case where the other two are not.** `V006/Datasheets`,
   `V006/Evt` and `X035/Datasheets`, `X035/Evt` are capitalised; this drop landed as
   `V003/datasheets`, `V003/evt`. `tools/verify_sdk_names.py` looks for
   `data/sources/<evt>/Evt` and resolves it on Windows because NTFS is case-insensitive —
   **it will not resolve on Linux or in CI.** This is the same defect class as the
   `ch32v00X.h` / `ch32v00x.h` mix-up, one directory level up. Renaming the two folders is
   the fix; not done here for the same reason as item 1.

5. **No `pio_env`.** All four variants have a PlatformIO *board*
   (`genericCH32V003F4P6` / `F4U6` / `A4M6` / `J4M6`), but `data/firmware/platformio.ini`
   defines no CH32V003 environment, so every `pio_env` is omitted rather than guessed.
   Adding `[env:CH32V003F4P6]` there would close the compile gate for this part the way
   `CH32V006F8P6` does for CH32V006 — the `--strict` gate is already green, so the
   generated C is believed to compile, but **nobody has run a compiler on it.** Do not
   round that up.

6. **The shorted-output question in "Shape 2" above.** It is the one hardware fact about
   this part that a later source could change.
